Request Routing, Admission Control, and SLO Tiers: Fallbacks and Graceful Degradation

Once a request clears the gateway's identity and rate-limit checks, one question remains before a single GPU cycle is spent: which backend, at what priority, and what happens if the answer is "none available right now." This module works through admission control (reject now vs. queue and hope), the dimensions that narrow a request to one backend, the SLO-tiered lanes that make "priority" mean something concrete, and the ordered cascade of fallbacks a platform runs through before it finally says no. After it, you can read an inference gateway's routing config and predict exactly which requests it will shed first under load, and why.

1. Where this sits in the request lifecycle

Module 21 traced the top of the gateway's request lifecycle: a virtual key is authenticated and checked against its budget, a parallel rate limiter validates requests-per-minute and tokens-per-minute across the global, key, user, and team levels, and only then does the request reach what LiteLLM's own architecture documentation simply calls "the Router" before a provider call goes out1. That single word, "Router," is doing a lot of work. Inside it are four separable decisions this module unpacks: whether to admit the request at all, which service-level lane it belongs to, which combination of model, region, and version it is allowed to land on, and — only at the very last step — which specific backend instance actually receives it. Module 25 picks up immediately after the fourth decision: once a backend is chosen, that module designs the interface across which the request actually crosses from platform to GPU serving stack.

Admission control and routing are not the same decision, and treating them as one is a common design error. Admission control answers a yes/no question — does this request get to consume any resource at all, right now — using information that is known before any backend is even considered: the caller's identity, its quota, and the platform's aggregate load. Routing answers a which question — given that the request is admitted, which of several compatible backends should carry it — using information about the backends themselves. Google's Borg cluster manager keeps this distinction explicit in its own architecture: quota-checking is described as "part of admission control, not scheduling: jobs with insufficient quota are immediately rejected upon submission"2, while the placement decision — which machines actually run an admitted job — is a separate, later step. Section 2 below builds on exactly this separation. An inference gateway that conflates the two ends up either rejecting requests it could have served (because it checked backend load before checking quota, and gave up too early) or accepting requests it cannot serve (because it checked quota and stopped, without ever asking whether any backend had room).

There is a second ordering subtlety worth stating plainly because the course's module numbers do not match the runtime order of events. Module 23 covers the billing hold that reserves a worst-case credit amount against a streaming request. That hold cannot be placed until the request's price is known, and price depends on which model and region actually serve the request — a fact this module's routing decision determines. So although billing is numbered before routing in this course (Module 23 precedes Module 24), the hold it describes is placed chronologically after this module's routing decision resolves, once Module 25's interface confirms which backend was selected. Figure 1 draws this explicitly: the billing box sits downstream of the routing box, not upstream of it, regardless of module numbers.

The reason this module exists at all — rather than reusing Module 1's load-balancing vocabulary wholesale — is that generic L4/L7 balancing was built for a different traffic shape. Round-robin, least-connections, and ip-hash algorithms (Module 1) assume requests are short, stateless, and roughly interchangeable in cost. The Kubernetes project's own announcement of its Gateway API Inference Extension states the mismatch directly: "unlike typical short-lived, stateless web requests, LLM inference sessions are often long-running, resource-intensive, and partially stateful. For example, a single GPU-backed model server may keep multiple inference sessions active and maintain in-memory token caches"3. A load balancer that only sees HTTP path and connection count has no way to know that one candidate backend already holds the exact prefix cache this request needs, or that another is one queued request away from violating its latency budget. The same announcement is blunt about the consequence: "traditional load balancers focused on HTTP path or round-robin lack the specialized capabilities needed for these workloads. They also don't account for model identity or request criticality (e.g., interactive chat vs. batch jobs)"3. Everything in sections 3 through 5 is the answer to that gap: dimensions that do encode model identity and criticality, and signals that do reflect real backend state.

It is also worth separating this module's admission control from Module 22's rate limits, because both run before a request is served and both can produce a rejection, which invites conflating them. A rate limit is a per-caller ceiling — it protects one tenant's fair share of the platform and answers "has this specific key, user, or team asked for too much, too fast." Admission control in this module's sense is a platform-wide capacity question, independent of any single caller's history — it answers "does the platform, in aggregate, have room to accept one more unit of committed work at this priority." A caller can be well within its own rate limit and still be rejected by admission control, if the platform's aggregate quota at that caller's priority is exhausted by every caller combined; conversely, a caller that trips its own rate limit never reaches this module's admission check at all, because Module 22's layer runs first and rejects on a completely different signal. The two layers are complementary because they protect against two different failure modes — one caller monopolizing capacity, and every caller together exceeding it — and a platform that only implements one of them is exposed to the failure the other one exists to prevent.

2. Admission control: quota checked at submission, not at scheduling

Borg is the direct architectural ancestor of Kubernetes2, and its admission-control design is the precedent this module's figure plan is built around. Every Borg job carries a small positive-integer priority, and Borg defines non-overlapping priority bands for different uses. In decreasing-priority order these are monitoring, production, batch, and best-effort (also called testing or free); for the purposes of the paper, "prod" jobs are the ones in the monitoring and production bands2. Tasks inside the production band are deliberately disallowed from preempting one another, specifically to stop preemption cascades in which a high-priority task bumps a slightly lower one, which bumps another, and so on2.

Priority alone answers "who wins a resource conflict." Quota is the separate mechanism that answers "who is even allowed to ask." Borg's paper defines it precisely: "Quota is expressed as a vector of resource quantities (CPU, RAM, disk, etc.) at a given priority, for a period of time (typically months)," giving as its own worked example "20 TiB of RAM at prod priority from now until the end of July in cell xx"2. The admission rule follows directly: "Quota-checking is part of admission control, not scheduling: jobs with insufficient quota are immediately rejected upon submission"2. Scheduling is a downstream, independent step — the paper is explicit that "a low-priority job may be admitted but remain pending (unscheduled) due to insufficient resources"2. That single sentence is the cleanest available statement of the two-decision structure this module opened with: admission is a budget check against a static allocation; scheduling (here, routing) is a live placement decision against real machine state, and a request can clear the first and still wait on the second.

Borg also documents the economics that make hard quota work as an admission gate rather than degenerating into either constant false rejections or unlimited overcommit. Higher-priority quota costs more than lower-priority quota, and "production-priority quota is limited to the actual resources available in the cell, so that a user who submits a production-priority job that fits in their quota can expect it to run, modulo fragmentation and constraints"2. Because users rationally overbuy quota to insulate themselves against future growth, Borg counters by overselling quota at lower priority levels — "every user has infinite quota at priority zero, although this is frequently hard to exercise because resources are over-subscribed"2. Quota allocation itself is handled outside Borg entirely, tied to physical capacity planning2; the admission check at request time is a fast comparison against a number that was decided somewhere else, in advance, which is exactly why it can run before any backend lookup and reject in microseconds. The "infinite quota at priority zero, usually unusable" pattern has a direct AI-platform reading: a best-effort or free tier that is nominally unlimited but sits behind every paying tier's quota is not a contradiction, it is the same oversell-at-the-bottom design Borg uses, and it is why a free-tier caller can be told its request was "accepted" and still wait far longer than a paid tier's stated budget — Module 22's usage-tier and workspace-budget structures are the AI-platform implementation of the quota vector this section describes; this module only needs the admission rule it enforces.

2.1 Worked derivation: quota headroom and the reject boundary

Take Borg's own example allocation — 20 TiB of RAM quota at prod priority in a cell2 — and extend it with an illustrative scenario to make the admission arithmetic concrete. Suppose a team's currently-running prod jobs commit 14 TiB of RAM against that 20 TiB ceiling, and a new job requests \(N\) replicas at 1.5 TiB of RAM each. Admission control does not ask whether any machine has 1.5 TiB free; it asks whether the *quota ledger* has room:

$$ \text{committed} + N \times \text{per-replica RAM} \le \text{quota} $$ $$ 14\,\text{TiB} + N \times 1.5\,\text{TiB} \le 20\,\text{TiB} $$

Solving for \(N\) gives \(N \le 4\). A request for a 5th replica is rejected at submission — before Borg's scheduler ever runs feasibility checking or scoring to find it a machine — purely because the quota ledger has no headroom left, independent of whether some machine in the cell is in fact idle. This is the mechanism, not a metaphor: a system that checks quota before scheduling can reject in the time it takes to read and compare two numbers, and it rejects a knowably-over-budget request even when spare hardware exists elsewhere in the cell, because admission control's job is to protect the allocation, not to find capacity. An inference gateway that reuses this pattern — a virtual key's committed token-spend against its allocated budget1 — gets the same property: rejection is a cache read, not a round trip to a model server.

2.2 Admission is not scheduling: feasibility and scoring as the next, separate step

Borg's paper is explicit that admission control and scheduling are two different algorithms running at two different times, and it is worth reading exactly how it describes the second one, because Sections 3 and 5 of this module are the AI-platform analog of it. Once a job clears quota and is admitted, it sits in a pending queue that Borg's scheduler "scans asynchronously," proceeding "from high to low priority, modulated by a round-robin scheme within a priority to ensure fairness across users and avoid head-of-line blocking behind a large job"2. That round-robin-within-a-priority detail matters and has a direct AI-platform equivalent: without it, one tenant submitting a very large job (or, on an inference platform, a burst of long-context requests) could monopolize its priority band's scheduling attention while every other tenant at the same priority waits behind it. Section 4's SLO lanes need the same fairness discipline within a lane, not just an ordering between lanes.

The scheduling algorithm itself has two parts, and both map onto this module's later sections. Feasibility checking "finds machines on which the task could run" — machines that meet the task's constraints and "also have enough 'available' resources — which includes resources assigned to lower-priority tasks that can be evicted"2. This is Section 3's candidate-set narrowing: model identity, region, tier, and version pin play exactly the role of Borg's constraints, cutting the machine population down to the subset that could conceivably run the task at all, before anything about relative goodness is considered. Scoring then "picks one of the feasible machines," and Borg's built-in scoring criteria are "minimizing the number and priority of preempted tasks, picking machines that already have a copy of the task's packages, spreading tasks across power and failure domains, and packing quality including putting a mix of high and low priority tasks on a machine"2. Read that list against Section 5: "picking machines that already have a copy of the task's packages" is precisely the same idea as prefix-cache and LoRA-adapter affinity — reward a candidate for already holding something the request needs, rather than making it fetch that thing from scratch. "Minimizing the number and priority of preempted tasks" is the same idea KV-cache utilization and queue depth serve for an inference backend: prefer a candidate whose selection disturbs the least already-committed work. Borg names this step scoring; the Gateway API Inference Extension's EPP names it picking the endpoint that "best achieves the configured objectives"5. The vocabulary differs; the two-phase feasibility-then-scoring structure, run strictly after admission has already succeeded, does not.

3. Routing dimensions: narrowing a request to one backend

Once a request is admitted, routing narrows an open-ended set of backends down to one. Four dimensions do most of the narrowing in practice, and they compose — each one shrinks the candidate set before the next is applied, rather than voting independently:

  • Model identity. The request names a model (or a model alias); only backends serving that exact model, or a version-compatible alternative, are candidates at all.
  • Region. Data-residency requirements, latency to the caller, or simple capacity placement restrict the candidate set to backends in one or more regions.
  • Tier/priority. An interactive request and a batch request may be forbidden from sharing the same physical pool even if both name the same model, because admitting the batch request onto the interactive pool would consume capacity the platform has promised to keep free for low-latency traffic (Section 4 makes this precise).
  • Explicit version pin. A caller that pins a specific model version — rather than accepting "whatever the alias currently points to" — removes every backend running a different version from the candidate set, even a newer one, because a pinned caller has contracted for a specific, unchanging output contract.

What remains after all four filters is a candidate set, not a single backend — and it is deliberately not narrowed further by the same static rules, because the fifth and final narrowing step needs information the first four dimensions cannot provide: which candidate is actually best positioned right now. Section 5 covers that step.

3.1 What "the Router" actually does: LiteLLM's fallback and retry layers

LiteLLM's own architecture documentation names the internal structure of its Router component as three sequential layers wrapped around the actual provider call: a function_with_fallbacks layer that "catches failures; moves to the next model group in fallbacks," a function_with_retries layer nested inside it that "retries on another available deployment in the same group," and only inside both of those, the actual litellm.completion() or litellm.embedding() call that executes the provider API request and translates its response back to a common format1. Read against the four-dimension filter above, this maps cleanly: a "model group" in LiteLLM's fallback layer is the output of dimensions 1, 2, and 4 (model identity, region, version) narrowed to a named, interchangeable set; "another available deployment in the same group" is exactly the candidate set Figure 3 produces; and the retry layer is what runs when a specific candidate in that set is unavailable, before the fallback layer gives up on the group entirely and tries a different one. Section 6 reuses this exact two-layer structure — retry-within-group, then fallback-across-groups — as the concrete mechanics behind two consecutive steps of the degradation cascade.

Version pinning deserves emphasis because it is the filter most often treated as a preference rather than a hard constraint, and getting that wrong breaks Module 25's contract. A caller that has validated its prompts, tool schemas, and downstream parsing against one specific model version is not asking for "the best available version of this model" — it is asking for the one it tested against. Routing that silently substitutes a newer version because the pinned one is momentarily unavailable produces output the caller's own validation never covered. This is why version pinning sits inside the routing-dimension filter (a hard exclusion, evaluated before any backend telemetry is consulted) rather than inside the backend-selection signal (Section 5), which is only allowed to choose among backends that already satisfy the pin.

4. SLO-tiered lanes: interactive, priority, and batch

A priority number by itself is not an SLO. Module 11 defines the distinction precisely: an SLI is a measured quantity, an SLO is a target for that quantity, and an SLA attaches a consequence to missing the target — this module does not re-derive that vocabulary, only applies it. What a lane actually needs to mean, concretely, is a bundle of three things that travel together: a latency budget (the SLI target), a queueing position relative to other lanes (what happens when demand exceeds capacity), and a fallback eligibility (whether this lane's requests are allowed to degrade under Figure 5's cascade, and to what).

Borg's priority bands are the closest documented precedent for exactly this bundling, even though Borg's paper frames it as cluster scheduling rather than API serving. The paper's own workload description states the difference in stakes directly: "the first is long-running services that should 'never' go down, and handle short-lived latency-sensitive requests (a few μs to a few hundred ms)... the second is batch jobs that take from a few seconds to a few days to complete; these are much less sensitive to short-term performance fluctuations"2. That is a latency budget (microseconds to hundreds of milliseconds for prod, seconds to days for batch) and a queueing tolerance (batch jobs can wait; prod requests cannot) bundled into one classification, exactly the shape an inference platform's lanes need. The production band's added guarantee — no intra-band preemption, so a prod task is never bumped by another prod task2 — is the fallback-eligibility half of the bundle: prod is the lane that is protected from a specific class of degradation that lower bands are not.

The Kubernetes Gateway API Inference Extension's own documentation names the equivalent concept for AI serving as serving priority: an operator can "specify that your models for online inference of chat tasks (which is more latency sensitive) have a higher priority than a model for latency tolerant tasks"5. The Kubernetes project's announcement of the same extension calls the underlying property request criticality, contrasting "interactive chat vs. batch jobs" as the canonical example pair3. Both sources describe the same bundling Borg's bands provide — a request's criticality determines both how it is scheduled under contention and how latency-sensitive its budget is — without either source enumerating a fixed, standardized set of band names the way Borg's four-band vocabulary does.

Two design consequences follow directly from treating tiers as bundles rather than as a single priority integer. First, a priority number that only affects scheduling order but carries no fallback-eligibility rule is silently unsafe under sustained overload: without a stated degradation path, an overloaded low-priority lane either starves indefinitely (no SLO was ever promised, so nothing is technically violated, but the caller has no way to know when to stop waiting) or it forces an operator to intervene by hand, which is precisely the ad hoc failure mode Section 6 argues should not exist as a separate "incident response" procedure. Second, because the production band's no-intra-band-preemption rule2 exists specifically to prevent preemption cascades, an interactive lane on an inference platform should carry the equivalent guarantee: an interactive request should never be evicted from its position by another interactive request, only by an explicit higher-criticality class or by the cascade in Figure 5. Mixing "priority as a scheduling tiebreaker" with "priority as an eviction weapon within the same tier" reproduces the exact cascading-preemption failure Borg's design deliberately forecloses.

In practice

A lane's latency budget and its bounded queue length are the same constraint viewed two ways, and the arithmetic is simple enough to do at design time. If a lane promises a latency budget \(B\) and the backend serving that lane completes one request every \(s\) seconds on average, a request sitting at position \(k\) in that lane's queue cannot finish before \(k \times s\) seconds have passed even if nothing else goes wrong — so the queue cannot safely be allowed to grow past \(k_{\max} = B / s\) requests without the tail of the queue structurally breaching the budget. This is exactly why queue depth (Section 5) is a leading indicator of an SLO violation rather than a lagging one: it crosses \(k_{\max}\) before any individual request's measured latency does. A platform that only alarms on measured latency finds out about the breach after it has already happened to some caller; a platform that alarms on queue depth against this bound finds out before the next caller is affected.

5. Backend-aware routing signals: KV-cache utilization and queue depth

Everything in Sections 3 and 4 narrows a request to a candidate set. Picking one member of that set is the job Module 1's classical algorithms (round robin, least-connections, ip-hash, weighted) were built for, and the Kubernetes project's own case against reusing them unmodified is direct: those algorithms "lack the specialized capabilities needed for these workloads. They also don't account for model identity or request criticality"3. The Gateway API Inference Extension's answer is to add a component that has access to information a generic L7 balancer never sees: live, per-backend model-server state.

The extension's central abstraction is the InferencePool, described as representing "a set of endpoints running a model server framework," paired with an Endpoint Picker (EPP) that "functions as an implementation of an Inference Router that will fetch metrics from whichever portion of the InferencePool endpoints can best achieve the configured objectives"5. Architecturally, the EPP is not a replacement for an existing gateway; it is bolted onto one. The documentation states this design choice explicitly: the project is "leveraging Envoy's External Processing Protocol to extend any gateway that supports both ext-proc and Gateway API into an inference gateway"5 — reusing an existing, battle-tested Envoy-class data plane rather than building a bespoke proxy from scratch, the same ext-proc extension pattern Module 21 introduces at the top of the gateway stack. The claimed payoff is stated plainly, if without a specific measured figure in the introductory documentation: model-server-aware, metrics-driven load balancing "has been proven to reduce the serving latency and improve utilization of accelerators in your clusters"5.

Two signals do most of the work, and they are complementary rather than redundant. KV-cache utilization reflects how much of a backend's attention-cache capacity is already committed to in-flight sessions — a backend at high KV-cache utilization can still accept a request, but doing so risks evicting or slowing other sessions already resident, and a backend that already holds the relevant prefix in cache is a better placement for a request that shares that prefix. Queue depth reflects how many requests are already waiting for a turn on the backend's compute, independent of cache state — a backend can have room in its KV cache and still have a long queue, if its GPUs are saturated by compute-bound requests rather than memory-bound ones. The Kubernetes project's announcement names both explicitly as the routing signals the extension introduces3, and the two together give the EPP a genuine picture of backend health that neither alone provides: cache pressure without queue pressure means "slow to reuse, fast to start"; queue pressure without cache pressure means "fast to reuse, slow to start."

The same extension exposes two further signals worth naming because they narrow the candidate set from Section 3 in a way none of that section's four static dimensions can: LoRA adapter availability, which routes a request toward a backend that already has the specific low-rank adapter it needs loaded rather than one that would have to load it first, and prefix-cache status, a more general form of the KV-cache-utilization signal that specifically tracks whether a candidate backend already holds the shared prompt prefix a request needs5. Both are properties of backend state, not backend identity — a backend does not statically declare "I serve model X with adapter Y," it reports "I currently hold adapter Y in memory," which can change from one moment to the next as other requests load and evict adapters. This is exactly the kind of information a static routing table, decided once at deploy time, structurally cannot encode, and it is why this signal layer has to sit downstream of Section 3's static filters rather than inside them.

6. The graceful-degradation cascade, and why this is incident response

Every mechanism in Sections 2 through 5 has a failure mode: quota can be exhausted, a pinned version can be down, an entire region can be unreachable, a candidate set can be empty. What a platform does next is not a separate "incident response" system layered on top — it is the same admission, routing, and SLO-tier machinery already described, run in a fixed order, under stress. Stating this precisely is this module's answer to a real gap: no source in this course's map documents "incident response for an inference platform" as its own topic, because the organizations that publish this material do not treat it as one either. LiteLLM's Router ships exactly two degradation primitives — a retry layer and a fallback layer1 — and Borg's paper describes what happens to an admitted-but-unschedulable job with the same plainness it uses for everything else: it stays pending2. Neither source frames either behavior as an incident.

The cascade has an order, and the order matters because each step is more expensive and more visible than the one before it. A platform that skips straight to region failover when a same-region retry would have worked wastes cross-region bandwidth and adds latency for no reason; a platform that downgrades a model before exhausting cheaper options degrades response quality when it did not need to.

  1. Retry within the same model group, possibly in another region. LiteLLM's retry layer "retries on another available deployment in the same group"1 — this is the cheapest recovery because it changes nothing about which model the caller gets, only which physical replica serves it. A version-pinned caller (Section 3.1) can still be served here, because the candidate set already excludes incompatible versions before this step runs.
  2. Fall back to a different model group. Only once retries within the original group are exhausted does LiteLLM's fallback layer "move to the next model group in fallbacks"1 — this is where a genuine model downgrade happens, and it is the first step in the cascade that can change the caller's output. It is safe only if two conditions hold: the fallback's output contract is compatible with what the caller's code expects (the same reason Section 3.1 treats version pinning as a hard filter, not a preference), and the operation being retried is idempotent, so that a partially-completed primary-model attempt does not double-execute or double-charge when the fallback model picks it up. Module 18 and Module 23 establish exactly this idempotency guarantee for the billing side of a retried request; this step depends on it holding.
  3. Queue. If no fallback group has room either, the request does not fail — it waits. This is precisely Borg's "admitted but remain pending (unscheduled) due to insufficient resources" state2, applied to a request rather than a job. A bounded queue with the SLO-tier lane's stated latency budget (Figure 4) is what keeps this step from becoming an unbounded wait: once a request would age past its lane's budget while still queued, the cascade proceeds to the final step rather than holding it indefinitely.
  4. Reject. Only after retry, fallback, and a bounded wait have all failed does the platform return an explicit rejection — the same admission-control refusal Section 2 describes, now triggered by exhausted real-time capacity rather than exhausted quota, but returned with the same HTTP-level signal (429 or 503) a caller's retry logic already has to handle.
Key insight

An "incident" on an inference platform is not a different code path from normal operation — it is this cascade running with a higher fraction of requests reaching steps 2 through 4 instead of resolving at step 1. A platform that has correctly designed admission control, routing dimensions, SLO tiers, and this cascade has already built its incident response; a platform that treats incident response as a separate on-call procedure is building a second system to duplicate the first one, usually badly, under worse conditions than the ones it was tested in.

The precondition worth restating from step 2, because it is easy to gloss over: a fallback is only as safe as the guarantee that re-running (or partially re-running) the underlying operation cannot corrupt state. Every fallback in this cascade is, structurally, a retry — of the whole request at a different backend, or of the same request against a different model. Module 8's idempotency-key vocabulary and Module 18's three-state (absent/in-flight/complete) ledger model are what make "just retry it somewhere else" a safe instruction rather than a data-corruption risk, and Module 23 extends that same model to a still-streaming, partially-billed request. This module assumes that machinery is in place; it does not re-derive it.

6.1 What the client is told at each step

Module 10 already establishes bounded queues and load shedding as the two general backpressure primitives every layer of this course reuses; what is specific to this cascade is which signal accompanies which step, because a client's own retry logic has to distinguish "try again immediately, somewhere else" from "stop and back off." Step 1 (retry within a group) and step 2 (fallback across groups) are, by design, invisible to the caller — LiteLLM's retry and fallback layers resolve inside a single client-facing request1, so from outside the platform a successful retry or fallback looks identical to a first-attempt success. Step 3 (queue) is where the platform has to start telling the caller something, because a caller with its own latency budget needs to know whether it is worth waiting. A queued request can be held open (the caller simply experiences added latency up to the lane's budget) or, once that budget is exhausted, answered with an explicit signal that more waiting will not help — the same 429/503 vocabulary Envoy AI Gateway already returns when a token estimate would exceed a limit4, reused here for a capacity rather than a budget reason. Step 4 (reject) is unambiguous: the request is refused, and the caller's own retry-with-backoff logic (Module 10) is the correct response, not an immediate resubmission, because an immediate retry into a still-saturated system only adds to the queue depth that caused the rejection in the first place.

Where experts disagree

Every source in this module agrees that a request must clear some gate before it consumes GPU cycles. They do not agree on what that gate should check, or when. Three real, currently-shipping designs answer the question differently, and the difference is not cosmetic — it determines whether a platform fails safely under sustained overload or merely fails slowly.

Admission is a hard quota check, decided before submission

Borg's admission-control design, the direct ancestor of Kubernetes2

Quota is a pre-negotiated resource vector, and "jobs with insufficient quota are immediately rejected upon submission"2, without ever consulting real-time backend state. The check is deterministic and cheap — a comparison against a number decided during capacity planning, not a query to any live system.

  • Rejects in the time of a lookup, before any resource is touched.
  • Protects the allocation regardless of whether spare capacity happens to exist elsewhere, which keeps multi-tenant cost and capacity guarantees meaningful.
  • Requires no knowledge of a request's true cost in advance.
  • Blind to real-time backend saturation: a request within quota can still find every candidate backend full.
  • Quota allocation is a manual, out-of-band process2, so it lags real demand shifts.

Admission is an estimate, corrected after the fact

Envoy AI Gateway's token-based rate limiting4

Because an LLM response's true token cost is unknowable until generation finishes, the gate checks whether processing would exceed a configured limit, admits if not, and only counts real usage against the budget afterward4. The gate is provisional by construction.

  • Works when true cost genuinely cannot be known at admission time — the common case for generative workloads.
  • Reconciliation (Module 23's hold-and-release pattern) keeps the ledger eventually accurate even though the gate itself is approximate.
  • Systematically over- or under-admits relative to the true limit, because the number it checks against is an estimate, not the eventual truth.
  • Under sustained overload, admitting on optimistic estimates and reconciling later means the platform discovers it is over budget only after resources are already spent — too late to have prevented the overload.

There is no formal admission gate; placement is telemetry-driven and always tries to find room

Kubernetes Gateway API Inference Extension's Endpoint Picker53

The EPP's stated job is to fetch live metrics and pick the endpoint that "best achieves the configured objectives"5 among an InferencePool's members. Its introductory documentation describes selection among available backends, not a formal accept/reject decision at the pool's boundary.

  • Uses the most accurate available picture of backend state — KV-cache utilization, queue depth, adapter and prefix-cache residency53 — information neither of the other two positions has access to.
  • Naturally load-aware: it will not send a request to the most-saturated backend when a less-saturated one exists.
  • "Best available" still finds an answer even when every candidate is badly saturated, because picking the least-bad option is not the same as refusing to add more load; without a paired admission gate this can let queue depth grow without bound.
  • Depends on a telemetry pipeline that itself has latency and can be stale under the exact load spikes it exists to handle.
Assessment

These three are not competing final answers to the same question; they are answers to three different questions that a complete platform must ask in a specific order. Borg's hard quota gate should run first, precisely because it is cheap, deterministic, and independent of backend state — it is the mechanism that keeps a single over-quota tenant from ever reaching the expensive parts of the pipeline, and it is the correct thing to check before anything else regardless of how well-instrumented the backends are. The Inference Extension's telemetry-driven placement should run second, among whatever the quota gate admits, because once a request is legitimately entitled to run, picking the backend with spare KV-cache and a short queue is strictly better than picking blindly — but it is not a substitute for the first gate, because "always find the best available backend" degrades gracelessly into "queue depth grows everywhere" once every backend is genuinely saturated, with no rejection signal to relieve the pressure. Envoy AI Gateway's estimate-then-reconcile pattern is the right tool for a narrower job: tracking a value, like true token spend, that cannot be known until after the fact — it belongs paired with Module 23's billing reconciliation, not used as the platform's only admission gate, because a gate that discovers overload after resources are spent has already failed at the one thing an admission gate exists to do. What would settle this in a specific deployment is a load test that drives sustained demand past capacity and measures which layer's queue actually grows unbounded first; whichever layer has no reject signal at all is the one that needs a hard quota check added in front of it.

What is changing

The Kubernetes Gateway API Inference Extension is the least settled piece of this module's grounding, and it is worth flagging precisely because its own documentation shows the seams. Its API reference is published in two forms side by side — a "v1 API Reference" and a "v1alpha1 API Reference"5 — without the introductory documentation itself stating which one is the current recommendation for a new deployment; the project also lists an InferencePoolImport type alongside InferencePool without fully specifying it in the introduction5. Read together, this is a project still moving fields from an alpha surface toward a stabilized v1 surface, which is normal for an extension this young — the Kubernetes announcement of the project is dated 2025-06-053 — but it means the exact object schema this section describes conceptually (InferencePool, EPP-selected objectives, serving priority) should be checked against the live API reference rather than assumed frozen, if you are implementing against it rather than just reasoning about the pattern. The three-way division this module's disagreement section describes — hard quota, optimistic estimate, telemetry-driven placement — is comparatively stable, because it reflects a structural difference in what information is available at each decision point rather than an implementation detail likely to be refactored away.
