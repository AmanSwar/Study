The Request Path: DNS, Load Balancers, Reverse Proxies, CDNs, and Edge Networks

Every request in every case study and every platform-design module in this course crosses the same handful of hops before it reaches code that does real work: a DNS lookup, an anycast-routed connection, a cache check at the edge, a load-balancing decision, a reverse proxy, and finally the origin. This module derives each hop from its own primary documentation — nginx's load-balancing algorithms, Cloudflare's CDN architecture, AWS's Elastic Load Balancing layer split, the TCP and TLS handshake specifications — so that afterward you can read a load-balancer config or a CDN topology diagram and predict exactly which requests land where, and build a latency budget for any request path this course throws at you.

1. The request as a chain of independent hops

Nothing in this module is complicated in isolation: DNS resolves a name to an address, a load balancer picks a backend, a reverse proxy forwards a connection, a cache either has the answer or does not. What makes the request path worth a dedicated module is that these simple operations chain together, and a chain of independent operations has two properties that are easy to underestimate coming from single-node systems work.

First, every hop is its own failure domain. A DNS resolver, an edge PoP, a load balancer, and a reverse proxy are four different pieces of software running on four different machines (often four different companies' machines), and each one can be slow, overloaded, or down independently of the others. Second, and this is the one that actually bites in production, tail latency compounds across a chain rather than averaging out. If a request has to wait on the slowest of several sequential or fanned-out calls, the end-to-end response time is not the mean of the individual hops — it is dominated by whichever hop happens to be in its own tail on that particular request, and the more hops or parallel calls a request touches, the higher the chance that at least one of them lands in its tail5. A service whose individual hops are each fast at the 99th percentile can still have a visibly slow 99th percentile once six of those hops are stacked in series, because the probability that none of the six is having a bad millisecond is the product of six probabilities close to, but not equal to, one.

This is also why the request path is a genuinely different kind of engineering problem from the one an ML-serving background trains you for. A KV cache, a batching scheduler, or a collective operation inside a single training job runs under a single administrative domain, with a scheduler that can see the whole system and a network you provisioned and tuned yourself. A DNS resolver you don't operate, an anycast network run by a CDN vendor, and an origin data center you do operate are stitched together by public protocols (DNS, TCP, TLS, HTTP) precisely so that none of the parties needs to trust or even know about the internals of the others. Every mechanism in this module — a load-balancing algorithm, a cache-placement policy, a proxy's buffering behavior — exists to make that stitching predictable despite the fact that no single party controls the whole path.

The rest of this module walks the chain in Figure 1's order: DNS and anycast routing (Section 2) decide which physical location a request's bytes first arrive at; load balancing (Section 3) decides which backend process within that location handles it; the reverse proxy (Section 4) decides what happens to the connection before a backend ever sees it; the CDN/edge tier (Section 5) decides whether the request needs to leave the edge at all; session affinity (Section 6) is the one policy that couples several of the above decisions together and is worth treating on its own; and Section 7 turns the whole chain into a number.

2. DNS resolution and anycast routing

Before a client can open a connection to anything, a name has to become an address. That step looks trivial and is the reason the rest of the path can behave the way it does: DNS is the only hop in Figure 1 whose answer the client is allowed to cache and reuse across many requests, so it is also the only hop where "fast" mostly means "already answered."

2.1 Recursive resolution and why caching dominates the cost

A client's stub resolver does not usually talk to the authoritative server for a domain directly. It hands the query to a recursive resolver (an ISP's resolver, or a public one such as Cloudflare's 1.1.1.1 or Google's 8.8.8.8), which does the walking on the client's behalf and hands back a single answer. When that resolver already has a cached, unexpired answer for the name, the cost of the whole lookup collapses to one network round trip: "if it can [answer from cache], then the time to answer is only the round-trip time for a packet from the client to the resolver"2. When it does not, the resolver has to walk the delegation chain itself — root server, then top-level-domain server, then the domain's own authoritative server — before it can answer and cache the result for the record's TTL.

This is why a resolver's own network placement matters as much as its software: a resolver that is itself reachable over an anycast network inherits the same nearest-location routing that Section 2.2 describes for CDN edges, which is precisely why Cloudflare states its explicit goal for 1.1.1.1 as "eventually we want everyone to be within 10 milliseconds of at least one of our locations"2 — a target for the client-to-resolver round trip, not for the occasional root/TLD/authoritative walk behind a cache miss. In practice the overwhelming majority of DNS queries for any popular domain are answered from cache somewhere in the resolution chain, because TTLs are chosen to make repeated lookups of the same name cheap; the recursive walk is the exceptional case, not the common one. The number that belongs in a latency budget for DNS, then, is the cached-answer number, and Section 7 uses exactly that figure.

2.2 Anycast: the same address, answered by whichever location is closest in the network's eyes

Once a name resolves to an address, how does that address get a packet to the right physical location out of hundreds of candidates? The mechanism a modern CDN or DNS operator uses is anycast: the identical IP address is announced from every data center in the network, and the Internet's own routing protocol — BGP — decides, for each network the request originates from, which announcement to prefer. Cloudflare's own architecture documentation states the property directly: with anycast, "incoming traffic is routed to the nearest data center with the capacity to process the requests efficiently," and because "multiple nodes have the same IP address, if one node were to fail, requests are simply routed to another node in close proximity" — failover is a side effect of the routing mechanism, not a separate system bolted on afterward1.

Two things about that mechanism are easy to get wrong from a naive mental model. First, "nearest" means nearest by BGP path selection, which typically reduces to the shortest AS-path (the fewest network-operator hops the announcement crosses), not the shortest physical distance — a request can be routed to a data center in a different city than the geographically closest one if that city's data center has a shorter AS-path from the client's network. Second, anycast is a property of routing to a location, not a property of what happens once the packet arrives there; a single anycast IP can, and typically does, front many physical machines behind a single data center's own internal load balancer (Section 3) — anycast solves "which building," load balancing solves "which machine in that building."

Cloudflare's documentation contrasts this directly with the alternative most engineers reach for by default — ordinary unicast DNS load balancing, where a domain resolves to different IP addresses depending on which data center's resolver logic answers the query. That approach has two structural weaknesses anycast does not: "clients may be geographically dispersed from the DNS resolver" they happen to use, so the routing decision is made on behalf of the resolver's location, not the client's, and the whole scheme depends on the "client's DNS server instead of client's IP address" as the signal for proximity1 — a resolver shared by users on different continents (which public resolvers like 1.1.1.1 and 8.8.8.8 explicitly are) breaks the locality assumption that DNS-based routing depends on. Anycast sidesteps the problem entirely by making the routing decision at the IP layer, on every single packet, using the client's own network path rather than a DNS answer that gets cached and reused by clients the resolver never sees again.

The practical consequence for the rest of this module: everywhere Figure 1 draws "Anycast edge," read it as "the BGP routing layer delivered this TCP SYN to the nearest capable data center already, before any application-layer decision happened." Everything from Section 3 onward — load balancing, reverse proxying, cache placement — operates inside whichever data center anycast just chose, on traffic that has already been narrowed from "anywhere on the Internet" to "this one facility."

3. Load balancing: layer 4 vs layer 7, and the four algorithms

Anycast (Section 2.2) narrows "anywhere on the Internet" down to one data center. A load balancer does the next narrowing: which of the (often hundreds of) backend processes in that data center actually handles this connection. Two questions have to be answered before a load balancer can do anything: how much of the request can it see, and by what rule does it pick a target. The first question is the L4/L7 split; the second is the choice among round robin, least connections, ip-hash, and weighted variants.

3.1 What "layer" buys and costs

The terms L4 and L7 refer to the OSI model layers a load balancer operates at, and the distinction is not academic — it determines what information is available to the routing decision and what it costs to get it. AWS states the two positions about as plainly as a vendor ever does about its own two competing products. Its Network Load Balancer "functions at the fourth layer of the Open Systems Interconnection (OSI) model. It can handle millions of requests per second"6 — it sees TCP/UDP segments, not HTTP requests, and picks a target using "a flow hash algorithm based on the protocol, source IP address, source port, destination IP address, destination port, and TCP sequence number," so that every packet in one TCP connection is provably routed to the same target for the life of that connection, without the load balancer ever parsing what is inside the segments6. Its Application Load Balancer instead "functions at the application layer, the seventh layer of the Open Systems Interconnection (OSI) model," and evaluates "listener rules in priority order" that can match on the URL path, the HTTP host header, individual HTTP headers, methods, or query parameters before selecting a target7 — routing decisions a pure L4 balancer structurally cannot make, because it never terminates or parses the HTTP layer at all.

That extra visibility is not free. An L7 balancer has to complete the TCP handshake and, for HTTPS, the TLS handshake, then buffer and parse an HTTP request before it can apply a single routing rule — CPU and memory per connection that an L4 balancer never spends, which is exactly why the L4 product is the one advertised for "millions of requests per second" and the L7 product is the one advertised for content-based routing, TLS-termination convenience, and Lambda/container-aware target registration67. Table 1 lays the trade-off out directly; the two are not mutually exclusive; AWS's own NLB documentation notes that a target group's target type can itself be "an Application Load Balancer"6 — i.e., L4 in front of L7 is a supported, named pattern, not a workaround, used when an operator wants NLB's static IPs, millions-of-connections throughput, and source-IP preservation as the Internet-facing tier, with an ALB doing content-aware routing one hop behind it.

3.2 Round robin, least connections, ip-hash, and weighted: mechanism and failure mode

Once a balancer has decided what it can see, it still needs a rule for picking among the healthy targets. nginx's own load-balancing documentation is the cleanest primary description of the four algorithms every L7 (and, in spirit, most L4) balancer implements, because nginx ships all four as literal one-line directives rather than as marketing names for proprietary logic.

Round robin is nginx's default: requests are distributed to servers in the upstream group in rotation, with no other information used. Its failure mode is that it treats every backend as equally capable of handling the next request, which is wrong whenever backends differ in capacity or whenever request cost varies — a backend that is still finishing a slow request receives the next request anyway, on schedule, regardless of how busy it already is.

Least connections (least_conn) fixes exactly that failure mode by routing to whichever healthy backend currently has the fewest open connections: nginx "will try not to overload a busy application server with excessive requests, distributing the new requests to a less busy server instead"8. Its own failure mode shows up when connection count is a poor proxy for actual load — a backend holding many idle long-lived (e.g. WebSocket or SSE) connections looks "busy" by this metric even though it is doing no work, and can be starved of new requests it could easily serve.

ip_hash routes by a hash of the client's IP address instead of by backend state at all: nginx hashes "the first three octets of the client IPv4 address, or the entire IPv6 address" and uses that to pick a server, which "ensures that the requests from the same client will always be directed to the same server except when this server is unavailable"9. This is the mechanism behind session affinity (Section 6). Its failure mode is skew: the hash function has no notion of how much traffic any one client generates, so a handful of high-volume clients hashing to the same backend can overload it while others idle, and — this is the operational trap — simply deleting a backend from the pool reshuffles the hash target for many unrelated clients at once; nginx's own fix is that "if one of the servers needs to be temporarily removed, it should be marked with the down parameter in order to preserve the current hashing of client IP addresses"9 rather than removed outright. ip_hash also cannot be combined with a backup server9, because a hash-selected backend that fails has nowhere well-defined to fail over to.

All four algorithms share one more failure mode worth separating out, because it is about detecting a dead backend rather than about picking among live ones: none of them are useful if the balancer keeps sending traffic to a server that is already down. nginx's default answer is passive health checking — "reverse proxy implementation in nginx includes in-band (or passive) server health checks. If the response from a particular server fails with an error, nginx will mark this server as failed, and will try to avoid selecting this server for subsequent inbound requests for a while"8. Two parameters on the server directive control the behavior: max_fails sets how many consecutive failed attempts mark a server down (default 1; 0 disables the check entirely), and fail_timeout sets how long it stays marked down before nginx "will start to gracefully probe the server with the live client's requests" and un-marks it if those probes succeed8. This is passive in the precise sense that the signal is real client traffic failing, not a synthetic probe running on its own schedule — which means the first request to a newly-failed server is guaranteed to fail before the balancer learns anything, a one-request tax every passive scheme pays that a separate active health-check loop (polling a health endpoint independently of real traffic) is designed to avoid.

Weighted load balancing is not a fifth algorithm but a modifier on the other three: a weight parameter on a server directive biases round robin (and, since nginx 1.3.1/1.2.2, least_conn and ip_hash too) toward heavier-weighted servers in proportion to their weight9. 4. Reverse proxies: TLS termination, buffering, and routing

A load balancer answers "which backend"; a reverse proxy is the piece of software that actually sits in front of the backend and mediates the connection — often the same physical process as the L7 load balancer (nginx is both at once), but worth separating conceptually because it has responsibilities that have nothing to do with picking a target.

The first responsibility is the one most operators reach for a reverse proxy for in the first place: TLS termination. Decrypting HTTPS is CPU work, and centralizing it at one proxy tier means backend application servers never handle certificates, private keys, or the TLS handshake at all — they receive plain HTTP over a trusted internal network. nginx's own configuration model makes the mechanism explicit: an HTTPS server block needs an ssl_certificate directive naming the public certificate — "sent to every client" — and an ssl_certificate_key naming the private key, which "should be stored in a file with restricted access"11. Centralizing termination at one tier means one place to rotate certificates, one place that needs the restricted-access private key, and — the point Section 3.1 already made from the AWS side — backend fleets that never pay the TLS-handshake CPU cost per connection at all.

The second responsibility is routing in the literal sense nginx uses the word: "when NGINX proxies a request, it: 1. Sends the request to a specified proxy server 2. Fetches the response 3. Sends the response back to the client"10. This sounds identical to what an L7 load balancer already does (Section 3.1), and at small scale it often is the same configuration block; the distinction sharpens once a service has more than one logical backend — a reverse proxy can send /api/* to one upstream group and /static/* to another, terminate TLS once for both, and let each upstream group run its own load-balancing algorithm from Section 3.2 independently.

The third responsibility is the one that is easiest to underrate: buffering. By default, "NGINX buffers responses from proxied servers. A response is stored in the internal buffers and is not sent to the client until the whole response is received"10. The point of this is to decouple two very different kinds of slowness. A backend generating a response quickly but a client downloading it slowly (a mobile connection, a client on a saturated link) would, without buffering, force the backend's connection-handling thread or worker to stay occupied for as long as the slow client takes to receive the bytes — exactly the resource-exhaustion failure mode Module 11 treats generally as the reason bulkheads and timeouts exist. With buffering, the backend hands its full response to the proxy and moves on immediately; the proxy, not the backend, absorbs the cost of a slow client trickling the response out over a slow link. The same logic runs in reverse for slow uploads, which is why proxies also buffer request bodies before forwarding them.

Note

All three responsibilities compose at one hop. A single nginx (or equivalent) process in front of an application fleet commonly terminates TLS, applies L7 routing rules, runs a load-balancing algorithm from Section 3.2 per upstream group, and buffers both the request and the response — four distinct jobs, one configuration file, one place in Figure 1's chain.

5. CDN and edge PoP topology: tiered caching vs. a purpose-built appliance

Section 2.2 established that anycast routes a request to the nearest point of presence (PoP); this section is about what that PoP does once the request arrives, and about the two structurally different answers the industry has converged on for "what infrastructure serves this content at all."

5.1 Tiered caching: edge, regional tier, origin

A CDN with hundreds of PoPs has a scaling problem that has nothing to do with any single request's latency: if every PoP independently caches content and independently falls back to the origin on a miss, then a piece of content that is popular globally but cached nowhere yet gets requested from the origin once per PoP — hundreds of redundant origin fetches for the same bytes, all within the content's first few seconds of popularity. Cloudflare's answer is to interpose a second, smaller tier of data centers between the edge PoPs and the origin: "with Tiered Cache, certain data centers are reverse proxies to the origin for other data centers, resulting in more cache hits and faster response times"1. A cache miss at a small edge PoP no longer goes straight to the origin; it goes to a regional tier that is itself shared across many edge PoPs, so the first miss anywhere in a region populates a cache that every other PoP in that region can then hit — the origin sees, at most, one fetch per region rather than one per PoP.

Cache Reserve extends the same idea one tier further: a persistent object-storage-backed cache layer with a long, explicit retention window, so that even content Cloudflare's normal edge tiers have evicted for being insufficiently "hot" can still be served without going back to the origin — but retention is not the same as permanent freshness. When the TTL on content held in Cache Reserve expires, "the content will need to be revalidated by checking the origin for any updates"1 before it can be served again; a long-retention tier still has to answer the same "is this still correct" question every TTL-based cache answers, it just answers it less often. Figure 4 draws the resulting three-tier shape: many edge PoPs, feeding a smaller number of regional tiers, feeding one origin.

5.2 Netflix Open Connect: the purpose-built alternative

Everything in Section 5.1 describes a multi-tenant CDN: many customers' origins, many content types, shared PoPs and shared regional tiers. Netflix's Open Connect takes the opposite structural bet — one tenant, one content type (video), appliances placed directly inside ISP networks or ISP-adjacent exchange points, with every layer of the stack tuned for exactly that workload rather than for generality.

The tuning shows up as a measured, multi-step throughput progression on a single FreeBSD-based appliance: CPU-limited at 40 Gbps on a single-socket Xeon E5-2697v2, then PCIe-limited once that CPU bottleneck was resolved, then into the 70+ Gbps range on updated hardware, then "well over 90 Gbps for the first time," and finally sustaining "100% TLS traffic comfortably at 90 Gbps" en route to a 100 Gbps target12 — a sequence of bottlenecks (CPU, then PCIe bus, then TLS handling) found and removed one at a time on hardware Netflix controls end to end, which a multi-tenant CDN operator generally cannot do for every customer's workload simultaneously.

The clearest illustration of purpose-built tuning paying off is a result that looks backwards until you see the mechanism: serving entirely from memory dropped throughput, it did not raise it. "The performance actually dropped from being CPU limited at 40 Gbps to being CPU limited at only 22 Gbps" when Netflix tried serving purely from RAM instead of NVMe storage12 — the memory-management overhead of the all-memory path cost more CPU than NVMe access did, on this specific hardware and workload. The resolution exploits video's own popularity distribution rather than fighting it: "10-20% of the most popular titles" stay resident in memory, and the long tail is served from NVMe12, a deliberate popularity-tail-aware placement policy that only makes sense because Netflix knows its content's popularity curve in advance and controls the appliance's storage tiers directly — a level of workload-specific tuning a shared regional cache tier serving arbitrary third-party origins has no equivalent lever for.

In practice

Even instrumentation is workload-tuned: Netflix found that "collecting detailed TCP statistics for every TCP connection consumed 5-10% of the CPU," a cost worth paying attention to only because the appliance is already CPU-bound at the limits above, and addressed it "by sampling only a small percentage of connections" rather than instrumenting every one12. A multi-tenant CDN carries this same instrumentation cost across every customer's traffic; Open Connect can decide, for its one workload, that most connections do not need per-connection statistics at all.

6. Session affinity and its cost

Section 3.2 already introduced the mechanism — ip_hash pins a client to a server by hashing its address9 — but it is worth isolating session affinity as its own design decision, because it is a policy choice about where state lives that happens to be implemented at the load-balancing layer, and it has real costs that a one-line config directive hides.

The default posture of round robin and least connections is explicitly stateless from the client's point of view: nginx's documentation states plainly that "with round-robin or least-connected load balancing, each subsequent client's request can be potentially distributed to a different server. There is no guarantee that the same client will be always directed to the same server"8. That is a feature, not an oversight — it is exactly what makes a fleet of backends interchangeable: any server can be drained, replaced, or scaled down without any client-visible discontinuity, because no client was ever tied to a specific server in the first place. Rolling deploys, autoscaling, and failure recovery are all cheaper when nothing downstream of the load balancer needs to know which server handled the last request.

Affinity trades that interchangeability away for a specific reason: "if there is the need to tie a client to a particular application server — in other words, make the client's session 'sticky' or 'persistent'"8 — meaning something expensive or hard to externalize is being held in that one server's process memory, and re-fetching or reconstructing it elsewhere on every request would be slower or more complicated than just always routing the client back to where it already lives. A WebSocket or long-poll connection is the clearest case: the connection itself is stateful at the TCP level, so once established, "affinity" is not even optional in the sense that all subsequent messages on that connection physically have to go to whichever server holds the socket — the design question is really about what happens on reconnection, not about the live connection. In-process caches, in-memory session data, or partially-built responses that have not been checkpointed anywhere shared are the cases where affinity is a genuine choice rather than a physical constraint.

The cost of that choice shows up in exactly the places statelessness was buying safety. Because ip_hash computes its target from a hash of the client address over the current server list, removing a server from that list — rather than marking it down — reshuffles the hash target for clients that had nothing to do with the server being removed9; a routine capacity change becomes an event that silently relocates other clients' state. And because ip_hash is incompatible with a backup server9, there is no clean failover target for a client whose assigned server actually dies — nginx falls back to "another server" on failure, but the guarantee that made affinity useful in the first place (this client always lands here) is exactly what breaks at the moment it would matter most. Module 2 covers the general alternative — externalizing session state into a shared cache so any backend can serve any client — and the trade-off it makes explicit is the one implicit here: a round trip to a shared store on every request, paid continuously, against an occasional expensive relocation, paid only on failure or rebalancing.

7. Building a latency budget end to end

Figure 1 sketched the chain; this section prices it, using only the round-trip counts and distance bounds each hop's own specification or documentation states, and being explicit about which numbers are measured facts and which are this module's arithmetic built on top of them.

Two protocol facts fix the handshake cost before a single application byte moves. Establishing a TCP connection is a three-way exchange — SYN, then SYN-ACK, then ACK — so no data can flow until one full round trip has elapsed3. On top of that, TLS 1.3 needs a further round trip: RFC 8446 describes the standard handshake as a single additional round trip, and states its 0-RTT early-data mode explicitly as "saving a round trip at connection setup for some application data, at the cost of some security properties" relative to that 1-RTT baseline4 — meaning the 1-RTT full handshake is itself the improvement 0-RTT is being measured against, and TLS 1.2's handshake, which 1.3 replaced, cost a second round trip that 1.3 removed. A fresh HTTPS connection therefore costs at least two round trips (TCP + TLS 1.3) before the first HTTP request can even be sent, and a third once that request and its response are counted.

Those round trips need a size, and the only sourced number in this map that stands in for "one round trip to an edge location" is Cloudflare's own reach figure: its network "spans hundreds of cities worldwide, reaching 95% of the world's Internet-connected population within 50 milliseconds"1. Using 50 ms as the round-trip unit is a simplification — it is a 95th-percentile distance bound across a whole global population, not a measured RTT for any specific request — but it is the only concrete, citable number available for "how far away is the nearest PoP," and it is a conservative one to plan against, since it already covers 95% of users. DNS is the one hop that mostly does not pay this cost at all: a cached answer costs only "the round-trip time for a packet from the client to the resolver"2, and Cloudflare's stated goal for its own resolver network is to keep that specific round trip under 10 ms2 — a tighter bound than the 50 ms CDN-edge figure because a DNS resolver network can be smaller and more aggressively distributed than a full CDN PoP fleet.

The gap between the two totals — roughly 4x on this arithmetic — is entirely explained by connection and cache reuse, not by anything a load-balancing algorithm or a faster proxy could fix. A warm client with a resumed TLS session and a cache hit pays exactly one round trip, no matter how the LB or reverse proxy tier is configured; a cold client paying for a fresh TCP handshake, a fresh TLS 1.3 handshake, and a cache miss pays for three additional round trips before Section 3's and Section 4's mechanisms even get to make a decision. This is also why HTTP/1.1 keep-alive, TLS session tickets, and high cache-hit ratios are, individually, worth far more to end-to-end latency than tuning which load-balancing algorithm runs behind the proxy — the algorithm changes which backend a request reaches; connection and cache reuse change how many round trips the request pays for at all.

Where experts disagree

Section 5 described two structurally different answers to "what serves this content at the edge," and the choice between them is a genuine, unresolved engineering trade-off rather than a matter of one side being wrong — Netflix and Cloudflare are both extremely well-resourced operators who looked at the same problem (serve bytes near the client, cheaply, at enormous scale) and built opposite architectures. Neither company has published a normalized per-gigabyte cost comparison, so the disagreement below is read from what each side actually built and argued for, not from a settled number.

Build a purpose-built, single-tenant appliance

Netflix's Open Connect engineering12

If your traffic is enormous, homogeneous (one content type, video), and has a well-understood popularity distribution, then owning the entire hardware and software stack lets you remove bottlenecks a shared multi-tenant platform structurally cannot remove for you: CPU, then PCIe bus, then TLS-handling limits, each found and fixed in sequence en route to 100 Gbps per appliance12. Storage tiering (10-20% of titles in memory, the rest on NVMe) and telemetry sampling are both workload-specific optimizations that only make sense because the operator knows its own content's popularity curve and is willing to tune for exactly that curve and no other12.

  • Per-byte efficiency: every layer, from kernel network-stack tuning to storage placement, is tuned for one known workload.
  • ISP placement: appliances embedded inside or adjacent to ISP networks shorten the physical path in a way a generic multi-tenant PoP fleet, sized for arbitrary customers' traffic, does not automatically get.
  • No shared-tenant contention for cache capacity, disk I/O, or CPU with unrelated traffic.
  • Requires the traffic volume and homogeneity to justify building and operating hardware at all — the memory-vs-NVMe and telemetry-sampling optimizations only pay for themselves at Netflix's scale.
  • No shared regional-tier benefit across tenants; every appliance's cache warms up against Netflix's own traffic alone.
  • All of the operational burden (appliance fleet management, ISP relationships, hardware refresh cycles) is now the content operator's job, not a vendor's.

Run on a general-purpose, multi-tenant CDN with tiered caching

Cloudflare's CDN reference architecture1

For anyone who is not shipping a single, massive, homogeneous content type, a shared network amortizes the PoP-building problem across every tenant at once, and a regional tiering layer recovers most of the purpose-built appliance's origin-offload benefit without any tenant owning hardware: a miss at one edge PoP is absorbed by a regional tier shared across many PoPs, so the origin sees roughly one fetch per region rather than one per PoP1, and Cache Reserve extends retention further still without a tenant operating any storage at all1.

  • Available immediately to any origin, at any traffic volume, with no hardware to build or operate.
  • Cross-tenant economies of scale: PoP and regional-tier capacity is shared across every customer's traffic, not sized for one workload.
  • Tiered caching recovers most of the "one fetch per region" benefit that motivated Netflix's own regional exploitation, without a dedicated appliance fleet.
  • Tuning is necessarily generic — a shared platform cannot rebuild its storage tiers, kernel network stack, or telemetry sampling around one tenant's popularity curve the way Open Connect does around Netflix's.
  • Cache capacity, disk I/O, and CPU at each PoP are shared with unrelated tenants' traffic, so one tenant's workload cannot claim the whole box the way a single-tenant appliance can.
  • Origin-offload still depends on the tiering configuration (Smart/Regional Tiered Cache) being enabled and correctly scoped; it is a feature to configure, not a guaranteed property of using a CDN at all.
Assessment

The two positions are not actually competing for the same customer. Below some threshold of traffic volume and content homogeneity, building an appliance fleet is a net loss — you pay the fixed cost of hardware, ISP relationships, and kernel-level tuning for a workload too small or too varied to earn it back, and a multi-tenant CDN's shared regional tier already recovers most of the origin-offload benefit for free. Above that threshold, with traffic dominated by one content type with a knowable popularity distribution — which is precisely Netflix's situation, and precisely why Open Connect exists rather than being a hypothetical — the purpose-built appliance's workload-specific tuning (memory/NVMe tiering by popularity, telemetry sampling, successive CPU/PCIe/TLS bottleneck removal) becomes available in a way no shared platform can offer any single tenant, because a shared platform cannot dedicate its tuning to one tenant's traffic pattern without disadvantaging every other tenant on the same hardware. Neither Netflix nor Cloudflare has published the crossover point in traffic volume or cost per gigabyte at which the trade flips, and that is the concrete number that would let anyone place their own workload on this line rather than reason about it qualitatively.
