Training Data Pipelines: Crawl/Ingest, Filtering/Dedup, Tokenization, and Sharded Datasets

A frontier pre-training corpus is not a dataset someone assembled; it is the output of a batch job that runs URL-level, document-level, and line-level deduplication, heuristic and learned quality filters, and domain/language routing over trillions of raw web documents before a single token gets tokenized. This module reads Meta's own disclosed numbers for that job — the only pipeline-level dedup/filtering account any frontier lab has published at this depth — as a text-specialized instance of the map/reduce and RDD-lineage machinery Module 9 already built, not a new compute paradigm.

1. Scale, cutoff, and why this is a batch job, not a dataset

Llama 3 pre-trains on a corpus of about 15T multilingual tokens, against 1.8T tokens for Llama 21 — roughly an 8.3x increase in two model generations, drawn from a mix of data sources containing knowledge up to the end of 20231. Meta's paper details one of those sources — the web-crawl pipeline covered in §2-§6 — at the level of specific thresholds and classifier architectures; it names "a variety of data sources" once and does not itemize what else besides web crawl contributes to the corpus, or in what proportion. This module, correspondingly, is a detailed account of the web-data pipeline specifically, not a claim that web crawl is the corpus's only input. The flagship 405B-parameter model is pre-trained on 15.6T text tokens at a compute budget of \(3.8 \times 10^{25}\) FLOPs1. None of that text arrives pre-cleaned. Meta's own account of how it gets from "a variety of data sources" to "high-quality tokens" is explicit about the mechanism: several rounds of de-duplication and data cleaning are applied to each data source, domains carrying large amounts of personally identifiable information (PII) are removed outright, and so are domains ranked harmful by Meta's safety standards or known to carry adult content1. That PII/safety domain-level pass runs before any of the dedup or quality stages this module covers in detail — it is a blocklist check, not a scored filter, and Meta's paper does not disclose the blocklist's contents or size.

Everything downstream of that first pass is recognizable as an instance of the map/reduce contract and the RDD lineage graph Module 9 derives in full: a small number of deterministic, coarse-grained transformations (extract, filter, group-by-key, reduce) applied to an enormous, embarrassingly-parallel input, with the property that any transformation's output can be recomputed from its inputs rather than checkpointed independently. This module does not re-derive that machinery. What it adds is the specialization: which transformations, in which order, with which parameters, produce a frontier-scale pre-training corpus out of a web crawl, and which of those transformations need a shuffle (Module 9's reduce side) versus which stay embarrassingly parallel (Module 9's map side). Section 8 makes that mapping explicit once the stages themselves are on the table.

Note on coverage

Llama 3's paper is, as of this writing, the only frontier lab's disclosure of pipeline-level deduplication and filtering parameters at this depth — specific thresholds (a repeat count, a bucket size, a classifier architecture), not just a one-line description of "extensive filtering." "Where experts disagree" below contrasts it with two smaller, single-purpose open corpora (RefinedWeb and FineWeb) that disclose comparable pipeline detail at a smaller scale. No source in this course's map documents experiment-tracking or evaluation-pipeline tooling for the pre-training data stage specifically — not "how Meta's data pipeline is monitored," not "how a candidate data mix gets promoted from experiment to production." That is a real gap in what any lab has published, not a simplification made for this module, and nothing below fills it with invented mechanics.

2. Text extraction and cleaning

The pipeline's first transformation is not deduplication — it is turning raw HTML into text worth deduplicating. Meta built a custom parser rather than adopting an existing one, and optimized it specifically for precision in boilerplate removal balanced against content recall, evaluating that trade-off against popular third-party HTML parsers tuned for generic article-style content and finding their own parser performed favorably1. The choice to build rather than buy here is the same category of decision Module 10 covers for service infrastructure generally (build a bespoke component when the general-purpose one optimizes for the wrong thing), applied to a parsing library instead of a gateway.

Two specific extraction decisions are worth carrying forward because they resurface later in the pipeline. First, pages containing mathematics and code content get their structure preserved rather than flattened to plain text, and the parser retains image alt attribute text specifically because mathematical content on the web is frequently rendered as pre-rendered images with the math also present in the alt attribute — dropping alt text would silently delete a large fraction of the web's actual math content1. Second, after experimenting with different cleaning configurations, Meta found markdown markup actively harmful to a model trained primarily on web data compared to plain text, and removes all markdown markers as a result1. That is a data-pipeline decision with a training-time consequence Aman will recognize from the inference side: a model that never saw markdown syntax in pre-training does not "know" what a bullet list or a code fence means as a distributional pattern, which is one reason post-training (Module 36) has to teach formatting behavior explicitly rather than assuming pre-training supplied it for free.

Everything in this section is a per-document, side-effect-free transformation: given one HTML page, produce one cleaned-text document, with no dependency on any other document in the corpus. In Module 9's vocabulary this is exactly a map — embarrassingly parallel, and the cheapest stage in the whole pipeline to scale out, because it never needs a shuffle. The stages that follow are not all so simple.

3. The three-level de-duplication cascade

Deduplication is not one pass; Llama 3's pipeline runs three, each at a different grain, each catching a different kind of repetition, and each with a different cost profile1. Coarser levels run first because they are cheap and remove the most volume per unit of work; finer levels run last because they are the only ones that can see the kind of repetition that survives the coarser passes. The ordering also tracks algorithmic cost directly: comparing a URL string against a set of previously-seen URLs is a single key lookup; computing a MinHash signature requires shingling and hashing an entire document's content before any comparison happens; counting line repetitions requires holding a frequency table across every line in a bucket, not just a signature per document. Running the cheapest check first and only handing survivors to the next, more expensive check is the same early-filtering discipline a query planner applies when it pushes a cheap predicate ahead of an expensive join — the general principle transfers even though nothing here is literally a database query.

  1. Raw crawl. Web documents enter the pipeline with URL-level repeats (re-crawled pages), cross-URL near-duplicates, and boilerplate lines all still present.
  2. URL-level de-duplication. Across the entire dataset, only the most recent version of each URL is kept1. This is a single group-by-key on the URL string — cheap, and it removes exact re-crawls before any content comparison runs.
  3. Document-level de-duplication. Global MinHash (following Broder, 1997, as Llama 3's paper cites it) runs across the entire corpus to remove near-duplicate documents1 — text that differs in wording but carries the same content, which a URL check cannot see because it can originate from a different URL entirely.
  4. Line-level de-duplication. An aggressive pass similar to ccNet (Wenzek et al., 2019, as cited) removes any line that appeared more than 6 times within each bucket of 30M documents1. Manual qualitative review confirmed this catches leftover boilerplate — navigation menus, cookie warnings — but also frequent high-quality text; Meta kept it anyway because empirical evaluations showed strong improvements1.
  5. Tagged output. Surviving documents carry forward into quality classification and language identification (§4-§5), which is where the retained fraction narrows again on a different axis.

3.1 Why MinHash and bucketed counting scale to a trillion documents

Both the document-level and line-level passes solve the same underlying problem: deciding whether two pieces of text are "the same enough" without ever comparing every pair of documents directly, which is quadratic and hopeless at corpus scale. MinHash1 sidesteps the pairwise comparison by turning each document into a small, fixed-size signature. Represent a document as a set of shingles (overlapping n-grams of words or characters); for \(k\) independent hash functions, compute the minimum hash value each function produces over that document's shingle set. A standard result for this construction is that the probability two documents share the same minimum hash value, for one fixed hash function, equals their Jaccard similarity \(J(A,B) = |A \cap B| / |A \cup B|\) — the fraction of shingles the two documents have in common relative to their combined vocabulary. Averaging agreement across \(k\) independent hash functions gives an unbiased estimator of \(J(A,B)\) that only requires comparing \(k\) small numbers per document pair, not the underlying text. For illustration — not a parameter Llama 3's paper discloses — take \(k = 128\) hash functions: two documents that are 90% similar by this measure would be expected to agree on roughly 115 of 128 minhash values, while two unrelated documents at 10% similarity would be expected to agree on roughly 13 of 128; the separation between those two expected counts is what makes a fixed similarity threshold usable as an automated near-duplicate test at any corpus size, without ever materializing the full intersection or union of two documents' shingle sets. In Module 9's execution-shape terms, computing the signatures is a map (one document in, one \(k\)-length signature out); grouping documents whose signatures collide into the same near-duplicate bucket is the shuffle-plus-group-by-key that makes this stage a reduce, not a map, even though no single "value" gets summed.

Line-level ccNet-style dedup is structurally the same computation Module 9 uses as its own introductory example, word count, with lines substituted for words. Map each line in a document to a (line-hash, 1) pair; group by line-hash within a fixed partition — Llama 3 fixes that partition at a bucket of 30M documents1 specifically so the count stays a bounded, local reduce rather than a global one across the entire multi-trillion-document corpus; sum the 1s per line-hash inside the bucket; filter out any line whose count exceeds 61. Bucketing trades recall for tractability: a boilerplate line repeated thousands of times across the whole corpus but fewer than 7 times inside any single 30M-document bucket would not be caught by this pass. Meta's manual qualitative review found the technique still removed frequent high-quality text alongside boilerplate, and kept it anyway because the net empirical effect was a strong improvement1 — a case where the aggregate result justified a mechanism known to have false positives.

4. Filtering for quality: heuristics, then trained classifiers

Deduplication removes repetition; it does nothing about a document that is unique but useless — a log dump, an SEO-spam page, a listing of outlier tokens no tokenizer should be spending vocabulary capacity on. Llama 3's pipeline handles that with two families of filter, run in sequence: cheap rule-based heuristics first, then trained classifiers on what survives1.

The heuristics are all pattern checks with a fixed, cheap-to-evaluate rule, not a learned model. A duplicated n-gram coverage ratio, following Rae et al. (2021) as Llama 3's paper cites it, removes lines made of repeated content such as logging or error messages — text that can be very long and unique enough to slip past line-level dedup's exact-repeat threshold, but still algorithmically detectable as "mostly the same n-gram over and over"1. A "dirty word" count, following Raffel et al. (2020)'s C4 methodology as cited, filters adult websites not already caught by domain block lists1. A token-distribution Kullback-Leibler divergence check filters documents containing an excessive share of outlier tokens relative to the training corpus's overall token distribution1 — a statistical anomaly filter rather than a content-based one.

What survives the heuristics goes to two model-based classifiers that Meta describes evaluating for this stage. The first is a fast classifier family (fasttext, following Joulin et al., 2017) trained to predict whether a given piece of text would be referenced by Wikipedia, following the same recognition target Llama 2's paper used1 — cheap enough to run over the entire post-heuristic corpus. The second is a more compute-intensive family built on RoBERTa (Liu et al., 2019a): Meta builds a training set of cleaned web documents, writes down the quality requirements in natural language, and has Llama 2's chat model judge whether each document satisfies them; a DistilRoBERTa model is then trained to reproduce those judgments and generate a quality score for every document at serving-time efficiency1. The paper describes both as classifier options it experimentally evaluated for this quality-filtering step; it does not specify whether production filtering runs them as a strict sequential funnel or combines their scores — that is a real gap in the disclosure, not a simplification made here.

Key insight

In Module 9's map/reduce vocabulary, running a classifier over every document is "just a map" — one document in, one score out, no shuffle. Cost-wise it is nothing like the cheap hash comparisons the dedup stages run. Scoring a corpus that survives dedup and heuristic filtering with even a distilled model like DistilRoBERTa is a batch-inference workload at a scale Aman would recognize from the serving side: one forward pass per surviving document, batched for throughput, with the same batch-size/latency and (at this volume) hardware-utilization considerations that apply to any other transformer inference job. The classic MapReduce/Spark cost model — dominated by shuffle/IO, with map and reduce functions themselves treated as cheap — does not hold for this particular map. The compute asymmetry this creates across the whole pipeline is worth its own accounting; §8.1 returns to it once every stage is on the table.

5. Domain-specific pipelines: code, math, and 176 languages

General web text and code or mathematical text have different statistics — different token distributions, different structural markers (indentation, LaTeX delimiters, code fences) — so a single quality classifier tuned on generic web prose is the wrong tool for either. Following the same approach DeepSeek-AI et al. (2024) took, as Llama 3's paper frames the comparison, Meta builds separate domain-specific pipelines that extract code- and math-relevant web pages1. Both the code and the reasoning classifiers are themselves DistilRoBERTa models, trained on web data annotated by Llama 2, but the annotation prompts are tuned specifically to target pages containing mathematical deduction or reasoning in STEM areas, and code interleaved with natural language1. Because the token distribution of code and math differs substantially from natural language, these pipelines also implement their own domain-specific HTML extraction, custom text features, and filtering heuristics rather than reusing the general web pipeline's extraction and heuristic stages unmodified1. This is a second full instance of the same map/reduce shape §2-§4 already described, forked on document type rather than chained after it. The custom HTML extraction matters concretely for this fork in a way it does not for the general web pipeline: a generic extractor tuned to preserve article-style prose will happily strip the indentation a code block's semantics depend on, or drop the LaTeX delimiters around an equation as if they were formatting noise rather than content — exactly the failure mode §2 already flagged for markdown, but sharper here, because indentation in Python or a missing closing delimiter in LaTeX does not just look worse, it changes what the text means.

Multilingual data gets its own parallel pipeline rather than a language-agnostic pass with a translation step bolted on. A fasttext-based language identification model categorizes documents into 176 languages1 — that count is the ceiling on how many distinct languages this pipeline can even route, since anything the classifier does not recognize cannot be assigned a language-specific downstream path. Within each identified language, Meta reruns document-level and line-level de-duplication independently1 — the same two algorithms from §3, re-applied per language rather than once globally, because a near-duplicate detector tuned on one language's byte and token statistics does not transfer cleanly to another. Language-specific heuristics and model-based filters remove low-quality documents within each language bucket, and a final multilingual quality-ranking classifier, itself based on Llama 2, ranks documents to make sure high-quality content is prioritized before the corpus-wide data-mix decision in §61. The actual proportion of multilingual tokens used in pre-training was determined experimentally, balancing English-benchmark performance against multilingual-benchmark performance1 — an empirical trade-off, not a fixed target set in advance.

Both forks — domain and language — feed back into one corpus before the model ever sees a token; §6 covers how the resulting categories get weighted against each other.

6. Determining the data mix, and annealing

Every stage so far decides whether a document survives. A separate decision — orthogonal to survival — is how much weight each surviving category gets once combined into one training stream. Meta's tool for this is a knowledge classifier: a model built specifically to categorize the kinds of information in the web corpus, used to identify categories over-represented relative to their training value (the paper names arts and entertainment as an example) so they can be downsampled rather than left to dominate the mix by raw crawl volume1. The classifier answers "what kind of knowledge is this," not "is this good," which is why it is a separate model from the quality classifiers in §4 rather than an extra output head on one of them.

The actual mix weights are not set by the knowledge classifier alone. Meta runs scaling-law experiments: train several small models on a candidate data mix, use the resulting scaling-law fit to predict how a much larger model would perform on that mix, evaluate the predicted-best candidate by actually training a larger model on it and checking benchmark performance, and repeat across mix candidates1. That loop — small-model proxy, extrapolate, validate at larger scale, repeat — is a search procedure over a low-dimensional space (category weights), not a filtering rule, and it is the step in this entire pipeline for which no source in this course's map documents any tracking or orchestration tooling: how many candidate mixes were tried, how long each proxy run took, or what infrastructure managed the search is not disclosed. Llama 3's own paper is explicit that this is not a bespoke technique invented for data-mix selection: it is the identical scaling-law methodology the paper uses elsewhere to pick the flagship model's parameter count, cross-referenced directly by Meta's own text1. One search procedure, reused for two different low-dimensional decisions — how big to make the model, and how to weight the categories that feed it — is itself a small illustration of this pipeline's general character: almost nothing about it is a novel algorithm, and almost everything about it is the disciplined reapplication of a small number of general techniques (hashing-based dedup, statistical heuristics, learned classifiers, scaling-law extrapolation) at a scale few organizations operate at.

One more transformation runs after the main mix is fixed: annealing. Late in pre-training, following Li et al. (2024b) as cited, Meta upsamples a small amount of high-quality data in select domains while linearly decaying the learning rate1. Deliberately, the annealing data excludes any training sets from commonly used benchmarks, specifically so that annealing's effect measures genuine few-shot and out-of-domain generalization rather than memorized benchmark answers1. Following OpenAI's own reported practice, Meta evaluates annealing's effect using the GSM8K and MATH training sets1: on the pre-trained Llama 3 8B model, annealing improved GSM8K validation performance by 24.0% and MATH validation performance by 6.4%; on the 405B model, the improvement was negligible1.

Meta also reports using annealing as a cheaper substitute for a full scaling-law sweep when judging whether a new candidate dataset is worth adding at all: anneal a partially-trained 8B model's learning rate linearly to zero over 40B tokens, weighting the candidate dataset at 30% against the default mix's 70%, and read the resulting benchmark delta as the dataset's marginal value1 — one 40B-token run standing in for what would otherwise require training multiple models across a range of compute budgets.

7. Tokenization and sharded-dataset production

Tokenization is the pipeline's last content-changing transformation, and the first one whose output format is dictated by the training system rather than by data quality. Llama 3 uses a 128,000-token vocabulary: 100K tokens come from the OpenAI tiktoken tokenizer, and 28K additional tokens are added specifically to improve support for non-English languages1. Compared to the Llama 2 tokenizer, this new vocabulary improves compression on a sample of English data from 3.17 to 3.94 characters per token1, and Meta reports that adding the 28K non-English tokens improved both multilingual compression ratios and downstream multilingual performance with no measured impact on English tokenization1.

A tokenizer's compression ratio is not a cosmetic statistic; it is a direct multiplier on how much raw text a fixed training-compute budget can cover, since compute scales with the number of tokens processed, not the number of characters those tokens represent.

Worked derivation: what a 3.17 → 3.94 chars/token improvement is worth

Define the compression ratio \(c\) as characters per token. For a fixed token budget \(N\), the amount of raw text "read" during training is

$$ \text{characters read} = N \times c $$

The relative improvement from Llama 2's tokenizer (\(c_2 = 3.17\)) to Llama 3's tokenizer (\(c_3 = 3.94\)) is

$$ \frac{c_3 - c_2}{c_2} = \frac{3.94 - 3.17}{3.17} \approx 0.243 $$

— about 24.3% more raw text represented per token, for the same training-compute cost, since training FLOPs are set by token count and model size, not by how many characters each token happens to encode1. Applying this to Llama 3 405B's actual pre-training budget of 15.6T text tokens1:

$$ 15.6\text{T} \times 3.94 \approx 61.5\text{T characters, vs. } 15.6\text{T} \times 3.17 \approx 49.5\text{T characters under the old tokenizer} $$

The same 15.6T-token compute budget corresponds to roughly 12 trillion more characters of raw text under the new tokenizer than it would have under Llama 2's — a real increase in how much of the curated corpus the model gets to see, purchased entirely at the tokenization stage, with no change to the dedup or quality-filtering stages upstream of it. This derivation combines two disclosed numbers from the same source1; Meta does not itself publish the "characters read" framing or the 12-trillion-character figure.

One packing detail belongs to this stage rather than to the storage layer, because it changes what the tokenized output actually represents. Independent documents get concatenated into fixed-length training sequences to avoid wasting positions on padding, and Llama 3 adds an attention mask that prevents self-attention between different documents packed into the same sequence1. Meta reports this had limited effect during standard pre-training, but found it important once continued pre-training moved to very long sequences1 — without it, a token near the start of one document could attend across a packing boundary into an unrelated document merely because they happen to share a training sequence, an artifact of how the sharding job packs documents rather than anything about the documents' actual content. This is the one place where a decision made by this pipeline (how documents get packed into sequences) has a direct architectural consequence downstream (a mask the model applies at every layer), rather than only a data-quality consequence.

What tokenization actually produces, mechanically, is the pipeline's terminal artifact: for every surviving, quality-scored, language-tagged, mix-weighted document, a sequence of integer token IDs, written out in the sharded, training-cluster-ready form the storage fabric in Module 33 serves from. Nothing in Llama 3's paper details the shard file format, shard size, or the sharding scheme's relationship to the parallelism-dimension layout (TP/CP/PP/DP) Aman already knows from distributed-training practice — that boundary is deliberately where this module stops and Module 33 picks up, since shard layout is a storage-and-serving concern, not a data-curation one.

8. This pipeline as a MapReduce/Spark batch job

Nothing in §2-§7 needs a new execution model. Every stage is either a deterministic function of one document (extraction, heuristic checks, classifier scoring, tokenization) or a deterministic grouping over a key derived from the documents (URL string, MinHash signature bucket, line-repeat bucket). Module 9 already named these two shapes precisely: map (k1,v1) -> list(k2,v2) for the per-record transformation, and the shuffle-plus-reduce (k2,list(v2)) -> list(v2) pattern for anything that has to group records by a derived key before it can finish. This module does not re-derive that contract or Spark's RDD-lineage fault-tolerance mechanism on top of it — Module 9 does that in full — it only places each stage from §2-§7 on one side of the map/shuffle line.

The fault-tolerance corollary follows directly from that placement, and Module 9 already proves it in general: if this pipeline is expressed as a chain of RDD-style transformations — map for extraction, filter for the heuristic and classifier stages, groupByKey/reduceByKey for the three dedup levels — then losing a partition of the final tokenized-shard output at any point does not require a checkpoint of that stage. It requires recomputing that one partition by replaying the same deterministic chain of transformations from the raw-crawl input, because every transformation in the chain is a pure function of its inputs and its position in the lineage graph. Nothing about operating this pipeline at trillion-document scale needs a different fault-tolerance mechanism than the one Module 9 already derived for cluster batch jobs generally; scale is a matter of how many machines run the same map and reduce tasks, not a change to what a map or reduce task is.

8.1 The compute asymmetry hidden inside the funnel

Figure 4 places every stage on one side of a map/shuffle line, and that placement is the right one for reasoning about fault tolerance and parallelism shape. It says nothing about cost, and the cost profile across those stages is wildly uneven. URL-level dedup, MinHash-signature computation, and the line-repeat counts are all bounded by hashing and integer comparison — CPU-cheap, memory-cheap, and (per §3.1) already parallel by construction. The heuristic filters in §4 are the same: an n-gram coverage ratio, a dirty-word count, and a KL-divergence check are all closed-form statistics over a document's own token stream, computed in time linear in document length with a small constant.

The classifier-scoring stage breaks that pattern. Running DistilRoBERTa — Meta's own choice specifically for the "efficiency reasons" the paper names1, meaning even the compute-intensive classifier family was distilled down from a full RoBERTa to make scoring the whole corpus tractable — over every document that survives dedup and heuristic filtering is a forward pass through a transformer encoder, for every one of what is, before this stage's own filtering narrows it further, a corpus on the order of the roughly 15T output tokens the final mix contains1. The domain-specific code and math classifiers and the multilingual quality-ranking classifier in §5 add three more full-corpus passes through a similarly shaped model. None of Module 9's classic cost intuition — that map and reduce functions are cheap and the shuffle is where the money goes — transfers to this stage without qualification: here, a "map" is a batch-inference job whose FLOPs count is plausibly comparable to some of the training runs that consume the corpus it filters. Meta's paper does not disclose the compute spent on classifier scoring itself, which is consistent with the coverage gap §1 already names: the data pipeline's own resource accounting is not part of what any frontier lab has published.

Where experts disagree

Llama 3's own recipe already blends heuristics, trained classifiers, and a knowledge-based downsampling classifier1, so it does not itself sit at either extreme of a live methodological split in how much a pre-training pipeline should lean on trained ML classifiers versus rule-based heuristics and rigorous deduplication. Two smaller, openly published corpora sit closer to the poles, and the gap between them is a real, cited disagreement about where the marginal engineering effort in a data pipeline is best spent.

Classifier-first: score hard, accept a much smaller corpus

Llama 3 (Meta, 2024)1 and FineWeb-Edu (HuggingFace, 2024)2

Train a model to recognize what "high quality" looks like — Llama 3's DistilRoBERTa classifier scored against Llama 2's own quality judgments1; FineWeb-Edu's classifier scored against Llama3-70B-Instruct's educational-quality judgments on a 0-5 scale2 — and accept that a large share of the crawl will fail the classifier's bar. FineWeb-Edu is the sharper illustration precisely because it is a single, disclosed transformation: the 15-trillion-token FineWeb corpus becomes a 1.3-trillion-token FineWeb-Edu subset2, an 8.7% retained fraction computed directly from those two published numbers, in exchange for what the paper reports as dramatically better performance on knowledge- and reasoning-intensive benchmarks such as MMLU and ARC2.

  • a learned classifier can encode a quality judgment (encyclopedic, educational, well-argued) that no fixed heuristic rule expresses directly
  • large, measured benchmark gains on knowledge/reasoning tasks specifically, not just perplexity
  • discards the large majority of the input corpus by construction — FineWeb-Edu keeps roughly 1 in 11 FineWeb tokens2
  • the classifier's notion of "quality" is itself a training artifact (judged by another LLM's preferences) and can homogenize style/topic distribution toward whatever that judge favored

Scale-first: filter with heuristics and dedup, keep almost everything that survives

RefinedWeb / Falcon LLM (TII, 2023)3

The paper's own title states the position directly: "Outperforming Curated Corpora with Web Data, and Web Data Only"3. RefinedWeb's MacroData Refinement pipeline runs document preparation, URL filtering, text extraction, language identification, and exact-plus-fuzzy deduplication over CommonCrawl, extracting five trillion tokens without a trained quality classifier deciding document-by-document retention3. The claim is that properly filtered and deduplicated web data alone — no curated books/Wikipedia/social-media corpus, no ML quality judge — can match or exceed models trained on curated corpora such as The Pile3.

  • preserves far more of the raw crawl's token mass, which matters once the target token budget (Llama 3 405B: roughly 15T tokens1) is itself close to or beyond what a classifier-first pass would leave behind
  • no dependency on another model's judgment (and that model's biases) to decide what counts as quality
  • heuristics and dedup alone cannot detect the specific kind of "low information density but not literally duplicated" text a learned classifier is built to catch
  • the paper's own benchmark comparison is against The Pile, not against a classifier-filtered corpus at equal token count, so it does not directly settle which approach wins at matched scale
Assessment

The deciding variable is the ratio between the target pre-training token budget and the size of the pool a classifier-first pass would leave. When that pool comfortably exceeds the budget — a small or mid-sized model, or a benchmark-driven project like FineWeb-Edu where the goal is maximizing knowledge-benchmark density rather than covering a fixed multi-trillion-token plan — classifying hard is close to free: you were going to discard most of the crawl anyway, so discard it on a quality signal instead of at random. When the budget approaches or exceeds the classifier-filtered pool's size — which is precisely Llama 3 405B's situation at roughly 15T tokens1 against a raw CommonCrawl that a hard classifier bar could shrink well below that — heuristics-and-dedup-first preserves the token mass a frontier run actually needs, and a classifier becomes a re-ranking or downsampling signal (as Llama 3's knowledge classifier and quality scores actually function, §4 and §6) rather than a hard gate. Llama 3's own pipeline is evidence for this reading, not a counterexample to it: it uses classifiers for scoring and category rebalancing, at a scale where a FineWeb-Edu-style 91% discard rate would leave far too little text for a 15T-token budget. What would settle this more cleanly than either paper alone: a head-to-head at matched token count and matched model size, classifier-filtered against heuristics-and-dedup-only, which neither RefinedWeb nor the FineWeb/FineWeb-Edu papers run against each other directly. Absent that experiment, the honest reading of the evidence available is that the two positions are not actually competing for the same design point — RefinedWeb and FineWeb argue about how to get the most out of a web crawl treated as the entire data supply, while Llama 3's mix (§6) treats "how aggressively to filter" as one tunable input to a scaling-law search alongside model size, sitting a level above either paper's single-axis claim.

What is changing

The direction of travel since Llama 3's July 2024 disclosure1 is toward more labs publishing pipeline-level detail, not less — FineWeb's own stated goal is to document and evaluate deduplication and filtering strategies openly enough that others can reproduce them2, and RefinedWeb published its MacroData Refinement pipeline specifically to make a scale-first, minimal-curated-data claim checkable3. Neither closes the gap this module opened with: both are single-purpose research corpora built to test one hypothesis, not the disclosed pipeline behind a shipped frontier model trained on the resulting data at 405B-parameter, multi-trillion-FLOP scale. As of this writing, that combination — pipeline-level dedup/filtering parameters and the frontier model actually trained on the output — still has exactly one public source. Experiment-tracking and evaluation-pipeline tooling for the pre-training-data stage specifically (as opposed to training-run monitoring generally, which is a different subject) remains undocumented by any lab in any source available for this course; a change worth watching for is any frontier lab publishing that layer with the same specificity Llama 3 gave the dedup cascade.
