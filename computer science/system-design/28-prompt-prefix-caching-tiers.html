Platform Prompt/Prefix Caching: Tiers, TTLs, and Billing Implications

A GPU-side inference engine reuses a shared KV-cache prefix for free, whenever it happens to see one twice. A platform turns that opportunistic reuse into a metered, priced, time-boxed product: a write you pay a premium for, a read you get a discount on, a clock that runs out, and — on one of the two major APIs but not the other — a rate limit the read doesn't count against. This module is about that product, not the cache itself.

1. Why this is a platform mechanism, not a KV-cache mechanism

The GPU-side mechanism is one you already have: when two requests share an identical token prefix, an inference engine can skip recomputing that prefix's key/value tensors and reuse the ones already sitting in the paged KV cache from an earlier request or an earlier turn in the same conversation. That reuse is opportunistic, free of charge to nobody in particular, and governed entirely by eviction policy and memory pressure inside the serving cluster. Nothing about it involves a customer, a price, or a clock. It is the substrate this module builds on top of, and this module does not re-derive it.

What Anthropic and OpenAI expose to a paying customer is a different thing wearing the same name. Both platforms let a client mark part of a prompt as reusable, and both platforms then do three things no GPU-side cache does on its own: they charge a premium the first time that prefix is processed (a "cache write"), they charge a discount every subsequent time it is found (a "cache read"), and they attach a time-to-live after which the entry is gone and the next request pays full write price again12. That is a billing-bearing product wrapped around a memory-management mechanism, and the product's rules — not the underlying KV-cache eviction policy — are what a platform engineer has to design against and what a customer has to reason about when deciding whether to mark a block cacheable at all.

Module 2 already covers the general vocabulary this specializes: cache-aside placement, TTL-based versus event-based invalidation, and the stampede problem of many readers racing a cold cache. Every one of those ideas reappears here in a form specific to LLM platforms — TTL expiry that a slow streamed response can itself cause (§4), a stampede variant where concurrent requests all miss because none of them has finished writing yet (§5) — and this module treats the general mechanism as background, cited by number, rather than re-explained. What Module 2's treatment could not anticipate, because no classical cache works this way, is that the miss/hit outcome here is also a metered event with its own price and its own interaction with a customer's rate limit (§6) — Module 22's territory, which this module specializes rather than restates.

Note

Everywhere this module says "cache," it means the platform-level, billed, TTL-bounded prefix cache a client opts into via an API parameter — never the GPU-resident KV cache the serving engine manages on its own. The two are related (the platform's cache write is, mechanically, a hint that keeps a prefix's KV tensors alive past the point they would otherwise be evicted) but the platform layer's contract with the customer is the subject here.

2. Two lookup philosophies: explicit breakpoints vs. automatic prefix match

Both platforms cache the same kind of thing — a prefix of tokens shared across requests — and both platforms turn a hit into a discounted read and a miss into a premium-priced write. Where they diverge completely is in how a request tells the cache what to look for, and that divergence has direct, practical consequences for how you author a prompt.

2.1 Anthropic: explicit breakpoints, walk backward on a hash

Anthropic's mechanism has three parts, stated as three "core principles" in its own documentation. First, a cache write happens only where a client places a marker: "marking a block with cache_control writes exactly one cache entry: a hash of the prefix ending at that block. The system does not write entries at earlier positions"1. Nothing is cached implicitly; if you never mark a breakpoint, nothing gets written, no matter how repetitive the prompt is. Second, a cache read does not search for "content that happens to be identical" in the abstract — it searches for a prior write. On every request, the system computes the prefix hash at the client's breakpoint, and "if none exists, it walks backward one block at a time, checking whether the prefix hash at each earlier position matches something already in the cache. It is looking for prior writes, not stable content"1. Third, that backward walk is bounded: "the system checks at most 20 positions per breakpoint, counting the breakpoint itself as position 1. If no matching entry is found in that window, checking stops"1. A single request may declare up to four such breakpoints, and the prefix they build on is assembled in a fixed order — tools, then system, then messages — so that "changes at each level invalidate that level and all subsequent levels"1: edit the system prompt and every message-level cache entry built on top of it is worthless on the next request, even though the messages themselves did not change.

The 20-block lookback window has a sharp practical failure mode in a long-running agent loop. Anthropic's own example walks through it directly: a ten-block first turn writes an entry at block 10; a fifteen-block second turn's breakpoint at block 15 walks back, finds the turn-1 entry at block 10 within the window, and extends it; but by a thirty-five-block third turn, checking positions 35 down to 16 no longer reaches the turn-2 entry sitting at block 15 — it is one position outside the window — so the request pays full price with no hit at all1. The stated fix is to plant a second, earlier breakpoint deliberately, closer to where the conversation was when it last wrote a cache entry, so that a fast-growing tool-calling loop does not silently walk itself out of its own cache. (Anthropic also folds a run of consecutive tool_use or tool_result blocks into a single position for the purposes of this count, so a turn with many parallel tool calls does not by itself push the window out1 — but the twenty-position ceiling is otherwise unforgiving.)

2.2 OpenAI: automatic, longest-to-shortest, machine-local

OpenAI's mechanism removes the marker entirely. There is no equivalent of cache_control; every request is automatically a candidate cache write, and every request is automatically checked against the cache on the way in. The lookup itself is a longest-to-shortest search: the system "walks through only the cache lookup boundaries in the incoming request, from longest prefix to shortest, looking for an available matching prefix already cached on the machine"2. On current models (GPT-5.6 and later) those lookup boundaries are "the first 2 and latest 50 explicit breakpoints" plus a set of implicit breakpoints and up to twenty earlier eligible message endingsa; on earlier models the only boundaries are implicit ones spaced at model-dependent intervals from the hidden system message2. Either way, reuse requires the entire rendered prefix up to that boundary to match exactly — "if content or a relevant setting changes before a breakpoint, the prefix after that change cannot match the existing cache entry"2, which is the same invalidation-cascade idea Anthropic states explicitly, arrived at without any client-visible breakpoint concept at all.

The word "machine" in that quote is doing real work and is easy to miss on a first read. OpenAI's cache is not a logical, request-routing-independent store; it is resident on whichever physical serving machine happened to handle the write, and a read only succeeds if the read request is routed back to that same machine: "cached states live on individual machines, where traffic above 15 requests per minute can lead to overflow routing. A request can reuse a cached prefix only if it reaches a machine holding a matching entry"2. Routing is driven by current machine load, by a hash of the initial tokens following the hidden system content, and optionally by a client-supplied prompt_cache_key that is described as important for pinning cache affinity on older models and optional on GPT-5.6 and later2. This is a genuinely different failure surface from Anthropic's 20-block lookback: a request can have an identical, well-formed prefix and still miss purely because load-based routing sent it to a machine that never saw the write. OpenAI states this plainly — "maintaining a session doesn't guarantee a cache hit"2 — and separately notes caches are isolated per organization and cannot cross a regional processing boundary2.

The practical upshot for how you write a client is opposite in each direction. Against Anthropic, you decide explicitly where the reusable boundary is and you must keep at least one breakpoint within 20 blocks of the last write in a fast-growing conversation. Against OpenAI, you do nothing to mark the boundary, but you may need to supply a stable prompt_cache_key and accept that even a byte-identical prefix can miss on pure bad luck in load-based routing. Neither is strictly simpler; they trade an explicit-but-bounded failure mode for an implicit-but-routing-dependent one.

In practice

An explicit breakpoint is a cost-control knob as much as a lookup mechanism: because a write only happens where you place cache_control, you decide exactly which prefix boundary is worth paying the 1.25×/2× premium for, and a request with no breakpoint at all never pays it. An automatic cache has no equivalent dial — every eligible request is a candidate write whether or not the caller expects the cost, which is simpler to integrate but removes the one lever Anthropic's design gives a cost-conscious client: the choice not to cache a particular prefix at all.

3. Pricing arithmetic: write premiums, read discounts, and the break-even hit rate

Both platforms price a cache event as a multiple of the ordinary, uncached input-token rate. Anthropic's standard multipliers are a 1.25× premium for a 5-minute cache write, a 2× premium for a 1-hour cache write, and a 0.1× discount for a cache read, with an exception on two current models (Claude Fable 5.1 and Claude Mythos 5.1) where the read discount is 0.025× instead1. OpenAI's current-generation (GPT-5.6 and later) multipliers are the same 1.25× write premium and 0.1× read discount; on earlier OpenAI models there was no separate write premium at all — caching was free to attempt, and the discounted cached-input rate was baked into each model's own published price rather than expressed as a multiplier2. That earlier-generation asymmetry is worth noticing on its own: OpenAI's move to charging a write premium on GPT-5.6+ is a convergence toward Anthropic's pricing shape, not a coincidence of two platforms landing on the same numbers independently.

3.1 When does paying the write premium pay for itself?

Write a cache write's multiplier as \(w\) and a cache read's multiplier as \(r\), both relative to the ordinary base input price for an \(L\)-token prefix (so a single uncached request against that prefix costs \(1\) unit, i.e. \(L\) tokens at the base rate). Consider the simplest case: one write followed by \(N\) reads, no misses in between. Caching costs \(w + Nr\) in total, against \(N+1\) units if every one of those \(N+1\) requests had instead paid the uncached rate. Caching is worthwhile once

$$w + Nr \le N+1 \quad\Longrightarrow\quad N \ge \frac{w-1}{1-r}.$$

For Anthropic's and current OpenAI's 5-minute-equivalent tier (\(w=1.25\), \(r=0.1\)): \(N^\ast = 0.25/0.9 \approx 0.28\). Because \(N\) must be a whole number of requests, this means the very first re-read of the prefix already crosses even: at \(N=1\), caching costs \(1.25+0.10=1.35\) units against \(2\) units uncached. A prefix you expect to reuse even once is worth marking cacheable under either platform's base tier.

That simple case assumes every request after the first is a hit — no TTL expiry, no concurrent cold miss, no routing miss. §4 and §5 show why that assumption breaks in practice, so the more useful version of this derivation treats the fraction of requests that hit, not the count of reads after one clean write. Let \(h\in[0,1]\) be the steady-state hit rate: the fraction of all requests against a given prefix that find it already cached, with the remaining \(1-h\) fraction each paying the write price (because each one is, from the cache's point of view, indistinguishable from a first write — TTL expired, routed to the wrong machine, or the lookback window missed). The expected cost per request, in the same units, is

$$\text{cost}(h) = (1-h)\,w + h\,r = w - h(w-r).$$

This is linear in \(h\): a straight line from \(\text{cost}(0)=w\) down to \(\text{cost}(1)=r\). Caching beats not caching at all exactly when \(\text{cost}(h) \le 1\), which solves to a break-even hit rate

$$h^\ast = \frac{w-1}{w-r}.$$

Plugging in the numbers: for the 5-minute Anthropic tier and current-generation OpenAI (\(w=1.25\), \(r=0.1\)), \(h^\ast = 0.25/1.15 \approx 21.7\%\). For Anthropic's 1-hour tier (\(w=2\), \(r=0.1\)), \(h^\ast = 1/1.9 \approx 52.6\%\) — more than double the hit rate needed to break even, because the 1-hour write premium is itself more than double the 5-minute one. For the two Anthropic models with the deeper 0.025× read discount, \(h^\ast = 0.25/1.225 \approx 20.4\%\), barely different from the 21.7% baseline — the write premium \(w\), not the read discount \(r\), is what dominates the break-even point, because the write premium sets the height of the line at \(h=0\) while the read discount only pulls down where the line ends at \(h=1\).

4. The TTL trap: cache lifetime is wall-clock from request start, not idle time

The break-even arithmetic in §3 assumed a hit rate you control by deciding to reuse a prefix. In practice the hit rate is also bounded by a clock, and the clock's exact starting point is where the trap sits. Anthropic's documentation is explicit about it: "the lifetime is measured from the start of the request that writes or reads the cache entry, not from the end of its response. Time spent generating a response counts against the lifetime: if a response takes 4 minutes to stream, a follow-up request that reuses the same cached prefix must start within about 1 minute of that response completing"1. The default lifetime is 5 minutes1, and none of those 5 minutes are reserved for the client's think time after the response finishes — the model's own token-generation time is drawn from the same budget.

This matters specifically because it is not the failure mode an engineer would guess from the name "5-minute cache." The naive mental model is "the entry survives for 5 minutes of idle time after the response is done," which would make almost any interactive follow-up safe. The actual rule is "the entry survives for 5 minutes from the moment the request that created it was sent," which means a slow generation directly eats into the window available for the next turn to land inside it. A reasoning-heavy response, a long tool-calling turn, or simply a large max_tokens budget on a verbose answer can each single-handedly consume most of the cache's usable lifetime before the user has even started typing the next message.

OpenAI's default retention is structured differently rather than just numerically differently, and the difference is worth naming precisely because it changes which workloads are exposed to this trap. On GPT-5.6 and later, an entry "remains eligible for reuse for 30 minutes after its most recent write or reuse"2 — a sliding window that resets on every hit, not a fixed clock from the original write. On earlier OpenAI models, retention depends on a configured policy: the default in-memory mode keeps an entry active for "around 5 to 10 minutes of inactivity, up to one hour," and an explicit 24-hour mode "typically keeps entries available for around 30 minutes and can retain them for up to 24 hours"2. Both of those are phrased around inactivity, which is the idle-time model a client would naively assume applies everywhere — it happens to be closer to correct for OpenAI's current defaults than for Anthropic's, though OpenAI's own documentation does not state explicitly whether response-generation time is excluded from that inactivity clock the way it is explicitly included in Anthropic's.

The operational consequence is direct: a workload built around Anthropic's default 5-minute tier and a long, reasoning-heavy or tool-calling turn should budget for the response time eating the window, either by moving to the 1-hour tier (at the 2× write premium and the correspondingly higher 52.6% break-even hit rate derived in §3.1) or by structuring the conversation so a fast, short exchange re-touches the cache before the 5 minutes elapse. Neither platform's documentation describes a way to extend a live entry's TTL without sending another request against it — there is no "keep-alive" call, only reuse itself.

This trap is sharpest exactly where Module 27's agent harnesses live: a multi-step tool-calling loop that pauses on a sandboxed code execution, waits on an approval gate, or simply runs a long reasoning turn before its next tool call can easily burn most of a 5-minute window on generation and wait time alone, long before the harness re-invokes the model with the same accumulated system prompt and tool list as its cache prefix. A harness that tracks its own elapsed wall-clock time since the last cache write — not just since the last response finished — is the only way to know, before sending the next call, whether it is about to land inside Figure 3's shrinking window or outside it.

5. Operational edges: minimum length, cold concurrent misses, invalidation cascade, no manual clear

Four smaller mechanisms decide whether the arithmetic in §3 actually applies to a given request at all, and each one is a place where a client that assumes caching "just works" silently pays full price without an error to warn it.

5.1 Minimum cacheable length

Both platforms refuse to cache a prefix below a minimum token count, and both do so silently rather than by raising an error. Anthropic's threshold varies by model, from 512 tokens on some current models up to 4,096 tokens on others1; "shorter prompts cannot be cached, even if marked with cache_control," and the only way to detect that this happened is to check the response's usage fields — "if both cache_creation_input_tokens and cache_read_input_tokens are 0, caching did not occur"1. OpenAI's current-generation threshold is a flat 1,024 visible input tokens; earlier models varied the effective minimum with request settings such as tools, images, output schemas, reasoning effort, and verbosity, and in both generations "tokens in the OpenAI-provided hidden system content do not count toward this minimum"2. A short, templated system prompt reused across thousands of small requests — exactly the shape that looks most cacheable to a developer — is precisely the case most likely to fall under either threshold and get billed as if caching had never been requested.

5.2 Concurrent cold misses

Module 2 covers the classical thundering-herd problem: many readers hitting an expired key at once, each independently regenerating the same value. The prompt-cache version is narrower but just as costly. Anthropic states it directly: "a cache entry only becomes available after the first response begins. If you need cache hits for parallel requests, wait for the first response before sending subsequent requests"1. Fire five requests against the same new prefix at once, and all five see an empty cache — every one of them writes, none of them reads, and the write premium is paid five times over instead of once. OpenAI's machine-affinity model (§2.2) produces a related but distinct failure: even after a first write exists, a burst of concurrent traffic against the same prefix — "traffic above 15 requests per minute can lead to overflow routing"2 — can scatter later requests onto machines that never received the write, so a request that would have hit at low concurrency misses purely because of routing load. Both failures point to the same operational rule: burst concurrency against a freshly-cacheable prefix is the one traffic shape prompt caching handles worst on either platform.

5.3 The invalidation cascade

Anthropic builds a request's cache prefix in a fixed order — tools, then system, then messages — and states plainly that "changes at each level invalidate that level and all subsequent levels"1. Add one tool to a tool list and every cache entry keyed on any system-prompt or message-level breakpoint built after it goes stale on the next request, even though the system prompt and messages themselves are byte-identical to before. OpenAI's automatic matching produces the same outcome from the opposite direction, without a named hierarchy: because reuse "requires the entire rendered prefix to match" up to a boundary, "if content or a relevant setting changes before a breakpoint, the prefix after that change cannot match the existing cache entry"2. A configuration change that looks purely additive — one more tool, one more few-shot example inserted near the top of a system prompt — is the change most likely to be made carelessly and most likely to silently invalidate an entire cache tier that a workload was depending on.

5.4 No manual clear, on either platform

This is the one place the two platforms agree rather than fork. Anthropic's documentation describes no API method to invalidate a cache entry on demand — the only lifecycle events are a write, a read, and TTL expiry. OpenAI states the absence explicitly: "manual cache clearing is not currently available. Cache entries expire according to the model's cache lifetime and retention settings"2. There is no operational lever equivalent to a CDN's purge API (Module 1) or an application cache's explicit DEL (Module 2) for either platform's prompt cache. If a cached prefix turns out to be wrong — a stale system prompt containing an error, a tool definition that needs to change immediately for a security reason — the only mitigation available is to change the prefix's content (which forces a new hash or a broken prefix match, i.e. a guaranteed miss on the next request) and wait out the TTL on the old entry, which then simply expires unread.

6. The rate-limit fork: do cached tokens count against your throughput ceiling?

Module 22 covers rate limiting as a general platform mechanism: Anthropic's continuously-replenishing token bucket against three dimensions (RPM, ITPM, OTPM)3 versus OpenAI's independent per-minute/per-day counters across six dimensions (RPM, RPD, TPM, TPD, IPM, and audio minutes per minute)4. What that comparison sets up but does not resolve is what happens to a cache hit specifically — and here the two platforms make opposite decisions with a large practical effect on any workload built around heavy prefix reuse.

Anthropic excludes cache reads from the input-token count that its ITPM limit measures: "for most models, only uncached input tokens (input_tokens + cache_creation_input_tokens) count toward your ITPM rate limits"3 — the read tokens, cache_read_input_tokens, do not count at all. Anthropic states the resulting effect directly with a worked example: "with a 2,000,000 ITPM limit and an 80% cache hit rate, you could effectively process 10,000,000 total input tokens per minute"3. The arithmetic behind that number is exactly the hit-rate framing from §3: if 80% of your input tokens are cache reads and only the remaining 20% count against the 2,000,000-token ceiling, then \(0.2 \times \text{total} = 2{,}000{,}000\) gives a total throughput of 10,000,000 tokens/minute — five times the nominal limit, purely as a consequence of how much of that traffic is a cache hit. Anthropic's 1-hour cache tier documentation frames this as a deliberate use case rather than an incidental side effect: one of its stated reasons to choose the 1-hour tier over the 5-minute default is "to improve your rate limit utilization, because cache hits are not deducted against your rate limit."1

OpenAI makes the opposite choice. Its prompt-caching documentation states plainly: "cached input tokens still count toward tokens-per-minute limits. Prompt caching does not change how rate limits are calculated."2 A request that is 100% cache hit, billed at 0.1× the base price, occupies exactly the same slice of the TPM ceiling as an equivalent request that missed entirely and was billed at full price. The discount is real; the throughput headroom is not.

OpenAI's column is flat at the nominal limit at every hit rate, by design.

The dollar consequence stacks with, rather than replaces, the throughput consequence. Take Claude Sonnet 5 at the prices in Table 2 ($2.00/MTok base input, $0.20/MTok cache read) against a fixed 2,000,000 ITPM ceiling and an 80% steady-state hit rate. On Anthropic, that workload's $-cost per token is already down to \(0.2\times\$2.00 + 0.8\times\$0.20 = \$0.56\)/MTok blended — a 72% price cut relative to the $2.00 uncached rate — and its effective throughput ceiling is simultaneously five times wider, at 10,000,000 tokens/minute, from §3.1's \(h^\ast=21.7\%\) break-even and Table 3's exclusion rule both pointing the same direction. On OpenAI, the identical 80%-hit-rate workload gets the same blended per-token discount but stays capped at whatever its nominal TPM limit already was: the price drops, the ceiling does not move. A capacity plan built by reading only the price list and ignoring which platform's rate-limit rule applies will be off by roughly the hit rate's own multiplier on Anthropic and exactly right, for the wrong reason, on OpenAI.

Where experts disagree

The two platforms this module has compared throughout do not just implement prompt caching differently — they have made an opposite, stated design decision about what a cache hit is for, and that decision shows up nowhere more concretely than in whether a cached token counts against a customer's rate limit. Neither company frames this as a debate; each states its own rule as a fact about its own product. Read side by side, the two rules are nonetheless a genuine disagreement about what a rate limit is supposed to protect.

Exclude cache reads from the throughput limit

Anthropic's ITPM design and its explicit 1-hour-cache rate-limit-utilization guidance31

A cache hit skips the expensive part of serving a prefill — recomputing key/value tensors for tokens the engine has already seen — so metering it identically to a token that forced a full prefill charges the customer for capacity the request never actually consumed a second time. Anthropic states the 1-hour cache tier is worth its higher write premium specifically because "cache hits are not deducted against your rate limit," and its rate-limit documentation gives a concrete payoff: an 80% hit rate against a 2,000,000 ITPM cap yields roughly 10,000,000 effective input tokens per minute.

  • Rewards efficient client design: a customer that restructures its prompts to maximize reuse gets a proportionally higher effective throughput ceiling without renegotiating a contract.
  • Ties the limit to the resource it plausibly exists to ration (prefill compute) rather than to a token count that no longer reflects new compute once it is a hit.
  • Makes capacity planning harder for the provider: a customer's effective consumption is now a function of a hit rate that can swing — a burst of first-time users, a config change that breaks the invalidation cascade (§5.3), a wave of TTL expiries (§4) — turning a stable-looking 2,000,000-token customer into a much larger one the moment their hit rate drops.
  • The limit stops bounding a single stable physical quantity; it bounds uncached tokens only, which is not the number a capacity planner can read off a dashboard without also tracking hit rate.

Count every token, cached or not

OpenAI's TPM design, stated without exception across model generations24

A cached read still occupies a slot in the serving path — it still has to be looked up, still holds a place in whatever KV-cache memory keeps it resident, and still contributes to the aggregate request the rate limit is shaping the arrival rate of. OpenAI's own language is unconditional: "prompt caching does not change how rate limits are calculated." One counting rule, applied uniformly regardless of how the tokens in a request were priced, is simpler to state, simpler to audit, and does not require a customer to model their own hit rate to know what their effective ceiling is at any moment.

  • A single, predictable ceiling: a 2,000,000 TPM customer is always a 2,000,000 TPM customer, independent of how cache-friendly their workload happens to be on a given day.
  • Simpler enforcement and a simpler mental model — no separate accounting path for cache-read tokens, no dependency on a hit rate the provider has to compute per customer per window to enforce the limit correctly.
  • A customer running a heavily-cached agentic loop — repeatedly reusing a long system prompt and tool list across hundreds of turns, exactly the workload prompt caching is marketed at — gets the price discount but none of the throughput benefit, and can hit the same wall a completely uncached workload would.
  • If the limit's real purpose is to bound the provider's prefill compute exposure, counting hits toward it is over-conservative: it caps the customer below what the underlying resource can actually support once most of their traffic is hits.
Assessment

Which rule is "right" depends on what physical resource a given rate limit is actually rationing, and that is exactly the fact neither platform's documentation discloses. If the binding constraint behind a customer's limit is prefill FLOPs — the compute a cache hit genuinely avoids — Anthropic's exclusion is the more accurate model, and it should become the more common design as serving engines increasingly separate prefill and decode capacity into distinct pools (the GPU-backend-handoff territory of Module 25): a limit on prefill-consuming tokens should track prefill-consuming tokens, and a cache hit is not one. If the binding constraint is instead something a cache hit does not relieve at all — resident KV-cache memory footprint held across the TTL, attention-serving slots occupied per request regardless of prefill cost, or simply a provider's deliberate cap on aggregate exposure to a customer's traffic independent of mechanism — OpenAI's uniform count is the more honest rule, because exempting reads would then be giving away headroom against a resource the reads still consume. Absent a published account from either provider of what specifically saturates first during a capacity incident — prefill compute (favors exclusion) or KV-cache-resident memory pressure (favors uniform counting) — this is not resolvable from outside either company, and a platform engineer's practical takeaway is narrower: know which platform you are integrating against before you build a heavy-cache-reuse workload's capacity plan around an assumed throughput ceiling, because the same hit rate produces a very different effective limit on each.
