System Design · Module 18

Stripe: Ledgers, Idempotency Keys, and API Design for Payments

Module 8 built the general vocabulary: a network only promises at-least-once delivery, and an idempotency key turns that into exactly-once effects by tracking a third state — in-flight — between absent and complete. This module is what that vocabulary looks like once the side effect is money: a durable in-flight state that survives a crash mid-request, an immutable ledger that records enough to make a retry provably safe, an exact backoff-and-jitter schedule a client library runs before retrying, and two competing designs — continuously-tracked balances versus end-of-period aggregation — for making usage visible before it becomes an invoice.

1. Why a payments API cannot just retry

Module 8 derives the underlying fact once and for all: no asynchronous network can tell a client, after a timeout or a reset connection, whether the server executed the request and the acknowledgment was lost, or whether the request never arrived. A client that wants the operation to eventually happen has exactly one option, retry, and exactly one new risk from retrying: the original attempt may have already succeeded, and the retry duplicates it. Module 8 also derives the fix — a client-generated idempotency key, a server-side record of that key's status, and a three-state model (absent, in-flight, complete) that a naive two-state read cannot represent safely. This module does not re-derive either of those; it takes them as given and asks what changes when the side effect the retry might duplicate is a movement of money rather than a generic write.

Nothing about the mechanism changes. Stripe's mutating endpoints accept an Idempotency-Key header carrying a client-generated identifier, and the server's behavior is exactly the three-state machine Module 8 derives: save the resulting status code and body of the first request made for a given key, "regardless of whether it succeeds or fails," so that "subsequent requests with the same key return the same result, including 500 errors"4. Stripe recommends a V4 UUID or an equivalently high-entropy random string, caps a key at 255 characters, and — this is the detail that makes the state machine durable rather than merely conceptual — automatically prunes keys once they are "at least 24 hours old," after which a reused key simply starts a new request4. If a client reuses a key with different parameters, the server treats that as a bug and errors rather than silently executing the new parameters or returning the old result4. None of this is specific to payments; it is Module 8's mechanism, instantiated at one HTTP header.

What is specific to payments is the cost of getting the in-flight case wrong. In a generic API, a duplicated write might create an extra row a cleanup job removes later. In a payments API, the two directions of failure both have a name and a customer-facing consequence: a retry misclassified as absent charges a card twice; a retry misclassified as complete tells a client an operation succeeded before the money has actually moved, and the client may act — ship the order, release the reservation — on a result that does not yet exist5. That asymmetry, not a different mechanism, is why this module spends the next two sections on how the in-flight state is made durable and what a ledger has to record, rather than on the state machine itself.

Note

An Idempotency-Key header only exists because POST is not idempotent by the HTTP specification's own definition — a second, identical POST is a new request as far as HTTP itself is concerned. Stripe's documentation is explicit that the header is scoped accordingly: "all POST requests accept idempotency keys," while "GET and DELETE requests... are idempotent by definition," so sending a key on either "has no effect"4. This is a narrower claim than Module 8's general idempotency-key pattern might suggest at first: the header is not a universal retry-safety wrapper, it is the specific patch for the one HTTP verb payments APIs use for money-moving operations that the protocol itself does not already make safe to repeat.

1.1 The same problem in the other direction: webhooks

Section 1's idempotency key protects one direction of traffic: client-to-server requests that mutate state. Stripe's platform has a second, symmetric direction — webhooks, where Stripe itself pushes event notifications to a merchant's server when something changes asynchronously (a dispute opens, a subscription renews, a bank confirms a delayed payment)6 — and that direction has exactly the same at-least-once problem, with the roles reversed. Stripe's own documentation states the delivery guarantee plainly: "webhook endpoints might occasionally receive the same event more than once," and the prescribed fix is the receiver-side mirror of Section 1's server-side cache: "guard against duplicated event receipts by logging the event IDs you've processed, and then not processing already-logged events"6. The merchant, not Stripe, now has to build the idempotency layer, because it is the merchant's handler that must not double-fulfil an order or double-apply a subscription renewal on a redelivered event.

The retry schedule on this side is Stripe's own, not a client library's: "Stripe attempts to deliver events to your destination for up to three days with an exponential backoff in live mode"6 if the merchant's endpoint fails to return a 2xx status — which is precisely why the documentation warns a handler to "quickly return a successful status code... before any complex logic that might cause a timeout"6, since a slow handler that eventually succeeds after Stripe has already timed out the request triggers a redelivery of an event that was, in fact, processed. Beyond that automatic window, a merchant can manually resend a specific event from the Dashboard "for up to 15 days after the event creation," or via the CLI "for up to 30 days"6 — three different retention windows (24 hours for an idempotency key's cached result, 3 days for automatic webhook redelivery, 15-30 days for manual resend) coexisting in the same platform, each sized for a different failure timescale.

Ordering is where this direction diverges most from Section 1's request/response case. A request and its retry are the same call, so ordering within that pair is trivial. A stream of webhook events is not: "Stripe doesn't guarantee the delivery of events in the order that they're generated"6 — creating one subscription can generate a customer.subscription.created, an invoice.created, and an invoice.paid event that arrive in any order, and the documentation's fix is the same identifier-based dedup, generalized: "track event IDs to identify duplicate deliveries instead" of relying on a timestamp, since "distinct events can share a timestamp"6. This is Section 3's business+id identifier and Module 8's offset-based ordering solving two different problems that look similar: Kafka's offset gives a total order within one partition by construction; a webhook event ID gives no ordering guarantee at all, only a guarantee that the same event, redelivered, is recognizable as a duplicate rather than a new fact.

2. Making "in-flight" a real, durable state

Module 8's Figure 5 marks the failure mode precisely: collapse a key's status to two values, and a request that arrives while the first attempt is still executing has no correct place to go — read as absent, it executes concurrently and duplicates the side effect; read as complete, it is served a result that does not exist yet. Stripe's documentation resolves the concurrent case by rejecting it as retryable rather than serving either wrong answer: "if... the request conflicts with another request that's executing concurrently, we don't save the idempotent result... You can retry these requests"4. That resolves what the server tells the client. It says nothing about how the server itself keeps track of "in-flight" durably enough to survive its own process crashing mid-request — and that implementation detail is exactly where a payments system earns or loses its correctness, because the in-flight window is precisely the interval during which a card has been authorized but the result has not yet been recorded anywhere a retry can find it.

Airbnb's payments engineering team published the clearest public account of how to implement this durably, in a 2019 post describing Orpheus, the idempotency library they built across their payments microservices5. Orpheus splits almost every API request into three phases — Pre-RPC, RPC, Post-RPC — and enforces two rules across them: no network calls in the Pre-RPC or Post-RPC phases, and no database writes in the RPC phase5. Pre-RPC records, in one database transaction, that this idempotency key is now in-flight — durably, before any network call happens. RPC is then free to talk to an external payment processor or bank over the network, because nothing about that phase is allowed to touch the database; a crash during RPC leaves the key visibly in-flight, not silently absent, because Pre-RPC's write already committed. Post-RPC then records, in a second database transaction, the outcome — success or a classified failure — and this is the write that moves the key from in-flight to complete5. Airbnb's stated reason for the strict separation is blunt: "network calls (RPCs) during the Pre and Post-RPC phases are vulnerable and can result in bad things like rapid connection pool exhaustion and performance degradation"5 — mixing an unreliable network operation into the same unit of work as a database commit means a slow or hung RPC can now also hold open a database transaction, which is precisely the kind of coupling Module 11's bulkhead-isolation material (Section on thread-pool vs. semaphore isolation) warns against for a different reason.

Two further details from the same design are worth carrying forward because Section 3 depends on them. First, Orpheus lets a caller choose between request-level idempotency, where a random key (Airbnb suggests a UUID, matching Stripe's own recommendation) scopes exactly one attempt-chain, and entity-level idempotency, where the key is deterministically derived from a business identifier — their example is the literal string payment-1234-refund — so that every caller asking to refund payment 1234 collides on the same key regardless of whether they generated it independently5. Stripe's documentation only describes the random, caller-chosen form4; Section 3's disagreement over which is better is not academic, it is a live design choice with production consequences on both sides. Second, every in-flight key carries an expiring lease — "a good rule of thumb is to have a higher lease expiration than the RPC timeout"5 — which is the same time-bounded-consensus-shortcut idea Module 6 derives for GFS's 60-second chunk lease and Spanner's 10-second leader lease, applied here to a single idempotency key instead of a whole replica or partition: a lease lets the system safely conclude "the original holder is gone" without waiting forever or risking two processes acting on the same key at once.

3. What a payments ledger must record

Stripe's own engineering account of its internal ledger system frames the problem it solves as a translation problem before it is a bookkeeping problem: Stripe moves money "through partnerships with local banks and financial networks in 185 countries" using "135 currencies and payment methods"2, and every one of those integrations has its own, incompatible notion of what a successful, failed, or pending operation looks like. Stripe's Ledger exists to translate all of that into one representation before anything gets recorded: "accounts are buckets of money distinguished by their type... and properties," and "events move money between accounts"2 — a charge, a refund, a payout are all, underneath, an event moving a specific amount from one named account to another. Stripe's own description of the resulting structure reaches for a physical analogy rather than an accounting term: modeling money movement is "similar to analyzing a flow of water through a network of pipes (processes) ending in reservoirs (balance sheets)"2, but the constraint doing the actual work is the standard double-entry rule underneath that image — every event that debits one account credits another by the same amount, so the books can be checked for balance without trusting any single component's arithmetic.

Two properties of this design matter specifically because retries and idempotency are the subject of this module. First, the ledger is described as "an immutable and auditable log"2 — an event is appended, never edited or deleted, which is the same append-only discipline Module 7 derives for GFS and Module 8 derives for a Kafka partition, applied here to money instead of file chunks or messages: if a mistake needs correcting, a new, compensating event is appended, the original event stays exactly as it was recorded, and the full history remains reconstructable. Second, out-of-order arrival is treated as normal rather than exceptional: "even if they arrive out of order, or are created by different sources, Ledger maintains accurate fund flows through the identifier for business and id"2 — the (business, id) pair is functioning exactly as an idempotency key functions in Section 1, except scoped to a ledger event rather than an HTTP request, and the ledger's correctness does not depend on events showing up in the order they were generated. At the scale Stripe discloses, that design choice is load-bearing: the ledger "sees five billion events" a day2, with "99.99% of... dollar volume... fully ingested and verified within four days"2 and, as a single stress data point, 300 million transactions totaling $18.6 billion in payment volume over the 2024 Black Friday weekend2.

That last row is not a hypothetical. Airbnb's own account of building Orpheus includes a worked failure mode from getting it wrong: they describe storing idempotency information on a database replica rather than the master, then walking through the sequence where "a client submits a payment request to the service, which ends up being successful downstream, but the client doesn't receive a response due to a network issue," the response is written to the master, and — because of replica lag — "the client could correctly fire an idempotent retry to the service and the response would not be recorded to the replica yet," so "the service could mistakenly execute the payment again, resulting in duplicate payments"5. Airbnb's fix was to read and write idempotency state only against the master database, accepting the latency cost, and to handle the resulting scale problem by sharding that table by idempotency key, which they note "have high cardinality and even distribution, making them effective shard keys"5. This is Module 5's PACELC trade-off (latency versus consistency, absent any partition) showing up at the smallest possible scope — a single lookup table — rather than at the scope of a whole storage system: a replica read is lower latency and, exactly as Module 3 derives for asynchronous replication generally, can be arbitrarily stale, and an idempotency check is one of the few reads in a system where that staleness has a direct dollar cost rather than a UX cost.

The same post is candid about where deterministic, entity-derived keys change the guarantee Section 1's random-key model provides. A purely random, client-chosen key (Stripe's only documented option4) gives you exactly one thing: this specific attempt-chain is retry-safe. It says nothing about whether two different callers, or two different code paths, might both try to refund the same payment using two different random keys — nothing stops that from happening twice, because the keys are different and the server has no way to know the two requests are, semantically, "the same operation." Airbnb's entity-level alternative — a deterministic key like payment-1234-refund5 — closes exactly that gap by making the key itself a function of the business fact being asserted, so that any caller, anywhere in the system, who tries to refund payment 1234 collides on the same row regardless of how many independent code paths generate the request. The cost is that the key space is now coupled to the business model — a new kind of operation on an existing entity needs a new, deliberately chosen deterministic key format, not just "generate a UUID and move on."

4. Automatic retries: backoff and jitter, with exact numbers

Everything in Sections 1-3 makes a retry safe; none of it makes retrying automatic. Stripe's own guidance on when a client should retry at all is narrow and explicit: "watch for 429 status codes and implement a retry mechanism... follow an exponential backoff schedule to reduce request volume when necessary, and add randomness to the backoff schedule to avoid a thundering herd effect"7. The same page names a second, non-obvious retryable case — an object lock_timeout, returned when "the Stripe API locks objects on some operations so that concurrent workloads don't interfere," and a request's lock acquisition times out because another request or internal process already holds it7. Unlike a rate-limit 429, Stripe's own SDKs retry a lock_timeout automatically, and the documentation's example sets this up explicitly: Stripe.max_network_retries = 27 — two retries, not an unbounded loop, and the client library, not the caller, decides the timing.

The timing itself is not left to guesswork; it is a fixed formula in Stripe's own client libraries. The stripe-node source computes a capped exponential delay and then applies jitter in two steps8:

$$ d_n = \min\!\big(d_0 \cdot 2^{\,n-1},\ d_{\max}\big) $$

where \(n\) is the retry attempt number, \(d_0\) is initialNetworkRetryDelay, and \(d_{\max}\) is maxNetworkRetryDelay. The library's defaults are \(d_0 = 0.5\) s and \(d_{\max} = 5\) s8. Jitter is then applied by scaling, not by adding noise: sleepSeconds *= 0.5 * (1 + Math.random()), which maps the uniform random draw to the range \([0.5\, d_n,\ d_n]\), and a final floor, sleepSeconds = Math.max(initialNetworkRetryDelay, sleepSeconds), guarantees the wait never drops below \(d_0\) even after jitter8. Because the floor sits exactly at \(d_0\) and the first attempt's uncapped delay is also \(d_0\), the very first retry has no effective jitter at all — the range \([0.5 d_0, d_0]\) gets clamped back up to exactly \(d_0\) every time. Jitter only starts to matter from the second retry onward, once \(d_n\) has grown past \(d_0\).

Worked schedule for the default constants

5. Two designs for usage visibility: continuous balances vs. end-of-period aggregation

Sections 1-4 covered mutating requests — a charge, a refund — where the ledger records a small number of discrete events per customer. Usage-based billing is a different shape of problem: a customer's account accumulates usage continuously (API calls, compute-seconds, tokens), and the question is not "did this one write happen exactly once" but "how far behind is the number we show the customer from the number we will eventually bill them." Stripe's own documentation lays out two designs for this and is explicit about which one it is steering new integrations toward.

The legacy path, Billing Meters, is architecturally simple: "you send meter events to the Stripe /v1/billing/meter_events endpoint and Stripe aggregates them at the end of the billing period"3. Stripe's documentation states the resulting staleness plainly rather than hiding it: "Stripe processes meter events asynchronously, so aggregated usage in meter event summaries and on upcoming invoices might not immediately reflect recently received meter events"3. The staleness bound here is not a fixed number of seconds; it is bounded by the aggregation cadence, which in the worst case is the length of the billing period itself — a customer's own dashboard, and Stripe's own invoice draft, can both be looking at a number that has not caught up to what actually happened in production a few minutes or hours ago.

The path Stripe now recommends for new integrations is Metronome, a usage-based billing platform Stripe itself operates, which "tracks running balances and usage totals continuously, so you and your customers can see current usage at any point during the billing period, not just at invoice time"3, and which Stripe's docs describe as "also built for high-volume ingest, making it more suitable for products where customers generate large numbers of events per second or per day"3. Metronome's own documentation describes three separate moments where usage is actually processed rather than just stored: "every time usage is sent, Metronome evaluates customer alerts and thresholds to send webhooks if spending limits are reached or credits are depleted"; usage is recomputed again "whenever the Metronome APIs are called, powering real-time dashboards"; and a final pass happens "at the end of the month or quarter" when an invoice is finalized9. The architectural move that makes this tractable is a deliberate separation between the raw fact and the billable quantity: a usage event is raw activity data sent "in the format that makes sense for your operations, without conforming to rigid predefined structures," and a billable metric is a separate, named transformation that "transform[s] raw usage events into meaningful quantities that appear on an invoice"9 — so a pricing change is a change to the metric definition, not a re-instrumentation of the application emitting events. Stripe's own integration guide for combining the two maps its native billing primitives onto Metronome's equivalents: a Stripe Meter corresponds to a Metronome Billable metric, a Stripe CreditGrant to a Metronome Prepaid commit, and a Stripe Credit balance to a Metronome Credit ledger10 — the same underlying concepts, named differently on either side of the integration.

The scale this design is built for is not hypothetical. In a customer case study Confluent (Metronome's streaming-infrastructure vendor) published, Metronome's own VP of Engineering, quoted by name, states the platform is "processing over 10,000 invoices per second and streaming billions of events per day with no lost data and extremely low end-to-end latency"11, elsewhere in the same case study rendered as "tens of thousands of invoices processed per second"11. At that ingest rate, an end-of-period aggregation design would need to run its aggregation job often enough to keep dashboards and spend-limit checks meaningfully current — at which point it is, in effect, reimplementing the continuous path anyway, just with an extra layer of batch scheduling on top.

The clearest case where the two halves of this module meet is a prepaid credit balance with auto-recharge: a customer draws down a balance of purchased credits, and the platform must charge them again once the balance crosses a threshold, without any manual step. Stripe's integration documentation describes exactly this as a supported pattern — "payment-gated commits (including threshold billing and auto-recharge), where a Stripe invoice must be paid before credits are released," with ACH support carrying "a 13-day payment window"10 — and this pattern needs both halves of the module simultaneously: it needs Section 5's continuous balance tracking to notice the threshold crossing while it is still true, and Section 1's idempotency-key-guarded charge to collect the recharge payment exactly once even if that request has to be retried. The documentation's own failure path shows what happens when the two halves disagree: "if a payment-gated auto-recharge payment fails, Metronome voids the invoice and disables the contract's auto-recharge," and a human has to "follow up with the customer and manually re-enable the contract"10 — a deliberate fallback to a non-retryable, human-in-the-loop state rather than an automatic retry loop, for exactly the reason Section 3's retryable/non-retryable distinction exists: a payment method that has already failed once is not a case where retrying with the same idempotency key is safe to keep doing unattended.

The choice between the two is not free, and it is not simply "always pick real-time." A continuously-tracked balance requires a streaming ingestion path that stays correct and low-latency under load — infrastructure the async design does not need at all, since a batch job that runs once per period can absorb backpressure that a real-time path cannot. The right question is what the staleness window actually costs: for a spend-capped or credit-metered product, a customer who can burn through their entire remaining balance in the interval between aggregation runs is a real, uncapped financial exposure, not just a stale dashboard — Stripe's own framing, "for products where customers generate large numbers of events per second or per day"3, is precisely naming the case where that exposure compounds fastest. For a low-volume, subscription-adjacent product where usage is measured in the hundreds of calls per billing period and no spend cap depends on real-time enforcement, the staleness window an async aggregation job introduces costs nothing a customer would ever notice, and building or paying for a real-time streaming path buys nothing.

Where experts disagree

Two design questions run through this module without a single settled answer, and both are visible in the primary sources rather than invented for contrast. The first is how far a single idempotency key can be trusted to make a workflow safe: is one key at one API boundary enough, or does a multi-step money-movement workflow need something closer to a saga? The second is whether usage visibility should default to real-time or asynchronous, now that Stripe itself operates both and states a preference.

A client-supplied idempotency key at the API boundary is enough

Stripe's production design14

Stripe's entire public idempotency mechanism is one header, one cached result, one endpoint. There is no workflow engine, no DAG, no compensating-transaction machinery visible in the documentation — a client retries a single call with the same key, and the server's cache does the rest. This handles the overwhelming majority of real-world failures, because the overwhelming majority of failures are exactly the case the mechanism targets: a dropped connection or a timeout around one already-idempotent operation.

  • Minimal moving parts: no orchestration framework, no DAG runtime, no separate compensation logic to build or maintain
  • Proven at Stripe's own scale and across arbitrary third-party client code, without requiring any cooperation from Stripe's internal services beyond the one endpoint
  • Only protects the single call it wraps; says nothing about what happens if the failure is between two of the platform's own internal service calls rather than between the client and the API
  • Provides no answer for an operation that has already produced an irreversible side effect and now needs to be undone, only for one that has not yet executed at all

Multi-step money movement needs systemic idempotency across a DAG of steps

Airbnb's Orpheus framework and payment-orchestration redesign512; the theoretical grounding is Garcia-Molina and Salem's saga model13

Once a single logical operation (charge the guest, pay the host, reconcile a resolution-center refund) touches more than one internal service, one idempotency key at one boundary does not cover the whole workflow — a crash between step 2 and step 3 of an internal DAG is invisible to whatever key guarded the original client-facing request. Airbnb's answer is to divide "every major workflow... into a directed acyclic graph (DAG) of retryable idempotent steps, each with well-defined behavior," reporting this design has "led to five 9s (99.999%) of consistency for payments" while volume simultaneously doubled125. But Airbnb's own account concedes the limit of pure idempotency: exceptions are explicitly split into "retryable" and "non-retryable," and a non-retryable failure after a partial side effect — a payment already authorized, a step that cannot simply be repeated — is a case idempotent retry cannot resolve on its own5. That is precisely the gap Garcia-Molina and Salem's 1987 saga paper names formally: a long-lived transaction broken into sub-transactions \(T_1,\ldots,T_n\) needs, for each \(T_i\), "a compensating transaction \(C_i\)" that "undoes, from a semantic point of view, any of the actions performed by \(T_i\), but does not necessarily return the database to the state that existed when the execution of \(T_i\) began"13 — a mechanism categorically different from "retry this step again," because retrying assumes the step never durably succeeded, and compensation assumes it did.

  • Extends retry-safety across an entire internal workflow, not just the one call a client happens to see
  • Makes the retryable/non-retryable distinction an explicit, audited property of every step rather than an assumption
  • Has a rigorous theoretical grounding (sagas) for the case idempotency alone cannot cover
  • Requires building and maintaining a workflow/orchestration layer most teams do not need for a single-endpoint operation
  • "Non-retryable" failures still fall back to "requires manual intervention" in Airbnb's own account5 — the framework narrows the gap sagas describe, it does not fully automate compensation

Real-time continuous metering should be the default

Stripe's own current guidance, steering new integrations toward Metronome310

Stripe explicitly recommends Metronome for new usage-based billing integrations and names high event volume as the case it is "more suitable" for3. A continuously-tracked balance closes the staleness window that an asynchronous design leaves open by construction, and the production numbers Metronome's own infrastructure vendor discloses — over 10,000 invoices per second, billions of events per day11 — show the approach scales past the volume most products will ever reach.

  • No staleness window for spend caps, credit thresholds, or fraud-relevant alerts to hide behind10
  • Decouples raw event instrumentation from billable-metric definition, so pricing changes do not require re-instrumenting the product10
  • Requires a correct, low-latency streaming ingestion path under load — infrastructure an async batch job does not need at all
  • Buys nothing for a product whose usage volume and billing sensitivity never make the staleness window observable

Asynchronous end-of-period aggregation remains the right default for many products

Stripe's continued support of the legacy Billing Meters path3

Stripe has not removed Billing Meters; it remains supported precisely because most usage-based products do not generate "large numbers of events per second or per day"3 and do not gate anything time-critical on the up-to-the-second balance. For that class of product, an aggregation job that runs periodically is simpler to build, has fewer moving parts to keep available, and the staleness it introduces is bounded by a billing period that customers never interact with at second-level resolution anyway.

  • No streaming infrastructure to build, operate, or keep available under load
  • Aggregation logic is defined once, at aggregation time, independent of how events happen to arrive
  • Staleness is bounded only by the aggregation cadence, which in the worst case is the full billing period3
  • Any feature that depends on real-time enforcement (spend caps, fraud thresholds) cannot be built on top of this path without adding a separate real-time check anyway
Assessment

Both contrasts resolve on the same axis: how expensive is staleness or blast radius, not which design is intrinsically better. For idempotency scope, a single client-supplied key is the right and sufficient tool exactly as long as the operation it guards is one call with one side effect at one boundary — which describes most of what a payments API actually does, and is why Stripe's documented mechanism stops there. The moment a logical operation spans multiple internal services with their own independent side effects, Airbnb's own numbers (five nines of consistency at double the volume) show that systemic, DAG-level idempotency is worth the orchestration cost, but even that framework's authors concede it narrows rather than eliminates the need for genuine compensation once a step's effect is irreversible — which is exactly the saga literature's 1987 claim, restated by production experience four decades later. For metering, the deciding variable is what staleness costs: if a customer can exhaust an uncapped exposure inside one aggregation cycle, or a fraud signal needs to fire before the next batch run, real-time tracking is not a luxury, it is the only design that closes that window; if usage is low-volume and nothing time-sensitive depends on the up-to-the-second number, the asynchronous path is simpler and costs nothing observable. What would settle either question further is the same kind of evidence in both cases: a published incident or postmortem showing a specific dollar loss traceable to the staleness window or the idempotency-scope gap, rather than the architectural description alone — Airbnb's replica-lag example in Section 3 is exactly that kind of evidence for idempotency scope, and no comparably specific public postmortem exists yet for the metering trade-off.
